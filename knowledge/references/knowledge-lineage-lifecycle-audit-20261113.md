## 1. 先分清三个经常被叫成“知识”的对象

1. **外部世界中的事实与现象**：一笔 Solana 原始交易、一次价格变动、一个软件运行故障、某论文的实验结果。它们各有观测条件、发生时刻、首次可见时刻、获取方式和覆盖。
2. **关于世界的表达与认识**：原作者描述、学科术语、程序设计假设、算法、市场机制推论、反例、竞争解释、风险判断。它们不是事实本身；“原文确实这样说”只证实**作者陈述存在**，不证实陈述对所有市场成立。
3. **系统实际具备的能力**：Blix 已有的源代码、数据流、服务、API、知识加载器、图谱、测试、运行中的工作流。程序“能加载段落”不等于“正确理解或使用段落”，CI通过不等于主网证实经济因果。

还应区分**人的目标**、**AI 产生的问题/方案**、**应用方授予的权限**。这三者不能由历史提示词、外部网页或项目作者自动接管。通用方法来自独立 [ai-d 知识维护规范](https://github.com/sunshihao001/ai-d/blob/main/knowledge/foundations/organization-protocol.md)，Blix 只采用适用的认知原则，不照搬 ai-d P1–P8 为交易产品架构。

## 2. 真正完整的流转关系：不应画成不可跳过的流水线

**认识形成网络**：
```text
用户现象/尚未表达的目标 ←→ 问题表征/隐藏前提
                   ↓                ↑
来源发现(项目/评论/论文/官方/书籍) → 原始版本与上下文获取
                   ↓
原作者目标、代码行为、测试、历史决策、数据合同的逆向理解
                   ↓
概念/事实主张/机制假说/失败反例/开放问题（各自标证据）
                   ↓
跨项目联系、冲突、替代机制、适用条件、尚缺证据
                   ↓
专业认识、尚未能裁决的争议，或更好的新问题
```

**产品承接网络**：
```text
专业认识 → 找原 Blix 已有事实/功能 → 适配性与成本/授权判断
              ├─ 只保留源链接、理论与开放未知
              ├─ 修正原 D01–D12 知识和旧错误认知
              ├─ 改调查问题、证据条件或报告字段
              ├─ 修改现有业务代码/增量测试
              └─ 启用经允许的只读工具/Agent上下文（可选择不启用）
                                         ↓
                                  离线回归/真实任务
                                         ↓
                            错误案例、反证、绩效与成本
                                         ↓
                         原位修订/限定适用/废弃默认启用/恢复待查
```

**从结果逆向追责网络**（更容易发现假知识）：
```text
用户看到的判断或报警
  → 哪项代码/模型产出？
  → 具体调用了哪个工具、知识版本、数据源？
  → 支持了哪一条主张，而不是哪整篇文档？
  → 原始签名/slot/交易指令、原源码commit、历史实验在哪里？
  → 取得时/生成时/首次可见时/用户收到时各是什么？
  → 哪些竞争解释、缺页、选择偏差、费用和失效条件仍存在？
  → 改变前后，是否能在同输入测试中重现？
```

这三张网络不是三次必须执行的步骤：简单事实查询可直接给出，长期开放研究可在“新问题—新来源—再解释”之间循环，实际修Bug可从失败测试逆向找到旧知识。

## 3. 逐个概念理解：各自的对象、作用、边界

| 概念（中/英） | 它究竟是什么 | 典型产物/不能混淆的东西 |
|---|---|---|
| **意图恢复 / Problem framing** | 从用户口语恢复已确认目标、约束与开放问题 | 问题模型；不能把AI新建议伪装成用户已选目标 |
| **发现 / Discovery** | 找到可能有价值的仓库、作者、论文、案例、评论和未知机制 | 来源候选、检索关键词；不是知识验收 |
| **获取 / Acquisition** | 取得可追溯的原始正文、代码、测试、Issues/PR/历史及版本 | 来源仓库、commit/blob、时间、许可证、页/行/交易签名；不是仅存URL |
| **审阅 / Inspection** | 实际看过哪些文件、数据及作者说法，区分遗漏范围 | 已读清单和未审清单；目录树扫描不算读完整个项目 |
| **逆向重建 / Reconstruction** | 从设计、代码、测试、故障、历史回推原问题、假设、限制和取舍 | “为什么这样设计”的受支持解释；代码无法直接证明作者心理动机 |
| **提炼 / Extraction** | 从原文中识别概念、主张、方法、事实、假设与反证 | 原文锚点+规范化表述；不能删去限定词只留标签 |
| **语义对齐 / Canonicalization** | 同义词、领域术语、字段、单位、钱包/TokenAccount、时间口径对齐 | 标准概念和别名；不是把不同东西强制统一 |
| **来源溯源 / Provenance** | 记录一条认识从哪些实体、活动与版本推导出来 | `source→claim→revision`；有链接不自动代表“主张被支持” |
| **证据归属 / Grounding** | 明确哪条原始事件/测试/结果支撑哪个具体主张 | 可复核证据引用，区分支持/反驳/无覆盖 |
| **知识融合 / Synthesis** | 在保留差异的前提下联结项目、机制和学科 | 新认识与竞争解释；两份转述同一来源不算两个独立证据 |
| **反证 / Falsification** | 寻找主张最可能不成立的条件和数据缺口 | 失败实例、能推翻结论的检查；不能过度保守到拒绝合理假说 |
| **承接 / Inheritance** | 明确旧知识在 Blix 原有系统的归位和使用目的 | 原 D01–D12、迁入位置和能力对应；不必复制一遍 |
| **转化 / Operationalization** | 将一项认识变成可执行观察、数据契约、报告、算法或测试 | 代码/字段/测试/查询；不是“用AI解释一下” |
| **检索与选择 / Retrieval + Routing** | 在当前任务中寻找最有用的知识和反例 | 可复查来源片段；11个白名单不等于全库自动检索 |
| **上下文组装 / Context engineering** | 将所选知识、事实、未知、源和任务限定提供给模型 | 受限上下文；外部文档不可提升工具授权 |
| **应用 / Application** | 知识是否改变真实问题、补查选择、解释或产品决定 | 明确前后差异；“已被调用”不等于“被正确应用” |
| **评估 / Evaluation** | 按相同数据、预算、时间点和对照检验事实正确、漏项、成本及收益 | 固定例/反例、模型A/B、样本外任务；写得长不叫提升 |
| **反馈与修订 / Revision** | 新证据改变旧主张的证据等级、边界或默认调用资格 | 保留旧版+新证据+修订理由；不要静默改写历史 |
| **退役与重开 / Deprecation + Reopen** | 错误/失效知识停止默认使用，待新证据再复开 | `SUPERSEDED/RETRACTED/UNKNOWN`，不意味着删掉原材料 |

重要差异：**保存（store）—索引（index）—检索（retrieve）—使用（apply）—验证（verify）—形成新知识（learn）** 是六个不同事实，不能用一个“已吸收”状态覆盖。

## 4. 来源怎么找才不会只停留在表面

优先按**原始信息量**和真实问题选来源，不是固定每次搜满某个数量：

- GitHub 完整成品：项目入口和目标→目录/主要业务链→关键数据结构→实现分支→测试与fixtures→Issues/PR讨论→历史提交/失败记录→许可证/依赖→可以复现的行为。既不能只读README，也不能按项目模块数量判定知识深度。
- X、Reddit、技术社区：原帖**和评论/反驳/复现链接**一起看；评论适合作为问题线索和经验反馈，匿名观点不可当成独立链上证据。多语言关键词应保留原语义及专业同义词，翻译后核原文。
- 官方协议、API、论文和经典书籍：分别适合锁定**协议要求、供应商数据合同、实证方法和长期理论机制**；作者声称和适用环境仍需核。
- 本项目历史：`grok/blix`现有源码、Hermes、qb-、meme-、ai-d、完整产品源码比营销列表优先；来源覆盖不足时允许扩大搜索，不由现有功能限制“什么知识值得发现”。

**复合证据陷阱**：若多个公众号/README都引用同一份未经核实的早期报告，它们是多个**传播渠道**，不等于多项独立观测。旧论文数据撤回后，保留研究问题但下调/停用对应数值结论。

**停止/继续标准**：继续检索应有希望改变主要解释、发现有价值的未知、反证、产品决定或真实验收；若只是重复来源而不改变任何判断，停止本支并标记尚缺条件。开放研究允许先保存“重要但尚无产品位置”的方法或假说。

## 5. 获取后究竟怎样理解和“承接”

同一个来源可能携带**八种不同的知识对象**，应用方式不同：

| 对象 | 示例 | 在现有Blix中的合适归宿 |
|---|---|---|
| 源事实 / SOURCE_FACT | Solana Token-2022 收费规则、RPC结构 | `knowledge/foundations` + 对应解析器契约/测试 |
| 作者陈述 / AUTHOR_CLAIM | 某成品自称支持多跳或98%识别率 | `knowledge/references`，不直接作市场真值 |
| 专业概念 / CONCEPT | Token Account/owner/authority/fee payer | 术语与别名映射，防止结构串台 |
| 方法 / METHOD | 边界化 BFS、失败样本对照、任务上下文选择 | 原 `knowledge/methods` + 适用/失败条件 |
| 机制假说 / HYPOTHESIS | 新钱包收币可能是转仓、托管或市场出货准备 | 原 D04–D07，提出区分证据，不自动贴庄家标签 |
| 可复现实例 / CASE | 同签名多 CPI、SOL→WSOL双计、历史回补假报警 | 原 `knowledge/cases` + Node fixture |
| 工程能力 / CAPABILITY | 现有 SQLite Mint 报告、钱包关系图、旧 BubbleMap | 已有模块增量维护；独立安全与验收 |
| 决策/目标 / DECISION | 当前只读、Blix主体、避免旧GMGN费用与重复系统 | `docs/project/goal-map.md`、`build-register.md`，不得由来源改写授权 |

实际承接有不同**合法结果**：完整保留原资料；仅登记来源与开放问题；研究后改当前理解；原位修正旧知识；补反例；改既有代码；适配现成成品；或拒绝/延后不适用方案。不是所有知识都要变成程序或固定Skill。

**保真约束**：原作者为何设计（文档可见）≠ 源码现在怎样运行（代码可见）≠ 我们推断为什么如此（研究解释）≠ 在真实Solana交易中能否成立（独立验收）。每次跨越需要明确证据或标为候选。

## 6. “知识关系”比“知识分类”更重要

仅有 D01–D12 标签无法说明因果、证据和冲突。可沿用 [ai-d 现有关系规范](https://github.com/sunshihao001/ai-d/blob/main/knowledge/foundations/organization-protocol.md)：

- `derived_from`：哪条主张来自哪份原始版本；`revised_from`：哪些解释发生了变化。
- `supports` / `contradicts`：具体交易/源码/反例支持或挑战**具体主张**；不能简单地说“论文支持钱包同控”。
- `applies_to` / `fails_when`：成立条件与失效条件，例如 Wallet Owner 不等于私钥/最终受益人。
- `related` / `broader` / `narrower`：语义相近和概念上下位，不能当资金流或因果关系。
- `implemented_by` / `tested_by` / `evaluated_by`：知识到现有代码、合成测试、真实验收和模型对照的可查关联。
- `changes_decision`：新证据如何改变用户操作、补查优先级、风险过滤或产品设计。
- `supersedes` / `retracted`：旧版本应停止默认引用，仍保留历史原文和修订原因。
- `unknown_because` / `reopen_when`：当前为何不可判断；未来得到什么来源或样本才有意义重开。

这类关系借鉴 W3C [PROV-O](https://www.w3.org/TR/prov-o/) 的 Entity/Activity/Agent 与派生、归因、修订语义；借鉴 [OpenLineage](https://openlineage.io/docs/spec/facets/) 的输入、输出、运行与版本概念。**本项目没有安装 PROV RDF 图谱或 OpenLineage 平台**，目前只需要在现有Markdown、manifest、代码测试里存储最少的可追溯关系。

**务必区分三种图**：资料/主张的“知识来源图”，GitHub/服务/任务的“软件执行依赖图”，Solana 钱包/Token 的“经济事件关系图”。它们可以引用彼此的调查结果，却绝对不能因为都有“节点/边”就互相冒充经济控制、事实证明或真实系统运行。

## 8. 两个真正的纵向案例：从原知识到可追责结果

### 案例 A｜“很多地址从同一个地方拿钱，是一组庄家吗？”

1. **原问题**：用户在一个 Mint 看见共同资金来源，怀疑共同控制或准备出货。不能先把“庄家”当真。
2. **旧知识出处**：`D05-K01`（SOL/Token/LP/补款边类型）原源 `knowledge/domain/L3-E-L3-02-capital-organization-incentives.md` → 迁入 `knowledge/mechanisms/capital-organization-and-incentives.md`；另查 Hermes 资金结构和 Why-Solana Dust 与中转多跳研究。
3. **专业重建**：SOL直接转入、Fee Payer垫费、Token转仓、CEX/池路由、多跳 Dust、同槽买入是不同经济对象。仅链上重复模式不证明同人。
4. **竞争解释**：共同控制、共享执行服务/公共设施、普通跟随市场热度、历史数据回补均可部分匹配；每种解释需不同的源事件、时间与账户角色。
5. **当前产品应用**：原 `server/bubble-funding-evidence.mjs` 纠 Fee Payer≠直接资助；`server/economic-events.mjs` 保留RPC原文；`economic-network.mjs` 对已捕获 Token Transfer 输出事件级关系和gross/net。**这个Token图还不是SOL资金来源图**。
6. **验收**：先测试同签名多CPI、地址Owner、错误池关联/空历史/转账后卖出候选；再用真实Mint检查漏采与公共设施。报告需要展示签名、outer/inner位置、source coverage；控制权 UNKNOWN。
7. **反馈**：如果发现某“共同资助”来自同一公共服务，修正相应候选关系和知识适用条件，不删除原交易，也不能认为所有其他同源都无价值。

`node scripts/audit-knowledge-trace.mjs --unit D05-K01` 可查**历史源→本地承接→AI可选状态**；它不代替真实Solana资金验收。

### 案例 B｜“这个钱包历史盈利，能不能直接跟单？”

1. **旧知识来源**：Hermes钱包角色、qb-关键钱包报告、meme-价格与阶段理论、Trading Portfolio成本方法；归原D04/D06/D08/D09。
2. **冲突**：钱包自己的买入成本与后来者可成交价不同；转入Token的**真实取得成本**和转入时**估值**不同；已实现收益与未实现价值不同。
3. **专业判断变化**：只有拿到观察者**首次可见时刻**、有效报价、退出路由、费用/滑点、失败/未参与Mint，才有资格谈可复制优势。不能把幸存钱包排行榜当样本总体。
4. **代码/测试**：`followability-replay.mjs` 仅评估输入的纸面收据，若报价过期/时间倒置/库存不连续则不给模拟收益；`audit-followability-offline.mjs` 是独立只读CLI。
5. **未完成**：真实模型使用了什么知识、哪份交易档案/历史报价完整、正收益是否样本外重复，尚没有实盘验证。即便每个测试都通过，也不得提升为已验证交易策略。
6. **后续修订**：假如真实样本中大量信号晚于价格异动，则降低此类钱包的“可跟随性”，却可能保留其用于风险排除或监控的价值。这是**知识改变任务目的**，不是简单删标签。

## 9. 证据等级不能设计成“经过五步便自动可信”

每个重要**主张**可以同时拥有以下不同证据维度：

| 维度 | 可以确定的事 | 不能跨越的事 |
|---|---|---|
| Source/Author | 找到原文/作者确实这么说 | 不能直接称事实正确 |
| Code/Test | 源码有该逻辑、针对固定fixture回归通过 | 不代表所有未知输入/主网均支持 |
| Provider/RPC | 指定时间供应商或RPC返回原始字段 | 不代表全链完整或控制权/因果正确 |
| Independent corroboration | 来源独立、方法兼容的另一证据支持该主张 | 转述/缓存同一数据源不能算独立 |
| Model usage | 模型确实选择了这份知识/工具并给出结果 | 不代表选对或解释正确 |
| Live validation | 真实授权环境对指定Mint和问题完成执行与复查 | 单样本不自动推广到所有发行和市场 |
| Out-of-sample | 冻结方法后对新的失败/成功全样本评估 | 不能把纸面收益直接当资金实际回报 |

因此每次新增认识至少应能回答：**主张是什么、来自哪里、适用范围、支持与反证、会改变哪个判断、下一条证据、当前状态**。复杂来源不必强制拆卡；只有需要机器查询、对比或执行验收时才增加结构化字段。

## 10. AI“知道知识”到底怎样被验证

现有11个白名单文件在**代码发现、允许读取、实际加载、正确选择、解释正确、结果更好**之间至少有六个互不等同的门槛。未来真正的 Agent 运行轨迹应能追到：
- 输入目标与明确Mint、问题表征；
- 知识选择的源路径/版本、为什么选、未选哪些重要反证；
- 每次只读工具和授权参数、原始证据覆盖、时间与错误；
- 模型推论与竞争解释、哪个具体事实支持哪句结论；
- 与无知识/旧路由/新路由的同任务评测差异、成本、延迟及误报。

[Google Skill Reach](https://google.github.io/skill-reach/)强调技能路由的漏选、碰撞、误选，而不是只看执行后的回答；[OpenAI Agent evals](https://developers.openai.com/api/docs/guides/agent-evals)说明用轨迹、测试数据集与评分器区分调用是否正确及最终表现。外部基准只能提供评估方法，**不代表本项目已完成模型A/B**。

**避免两种反效果**：过于严格地要求一手主网证据才能提出任何新机制，会停滞在已有问题；反过来让AI用流畅的叙述把旧未校准阈值、撤回文献和数据缺失补成事实，会制造虚假专业性。合理的中间态是“有理论依据的候选解释，指定可推翻条件；在有条件时做离线验证，再做真实实证”。

## 11. 在当前仓库怎样实际用追溯工具

无需安装新的图数据库或AI知识框架：

```bash
# 全局概览：本地迁入、152旧单元、21快照、11白名单的关系与断点
npm run audit:knowledge-trace

# 从旧知识单元回溯原始文档与新承接文件
npm run audit:knowledge-trace -- --unit D05-K01

# 从已承接的Blix知识文件逆向找旧来源及关联单元
npm run audit:knowledge-trace -- --target knowledge/mechanisms/capital-organization-and-incentives.md

# 输出全部可回查的静态对应（仅标准输出JSON，不修改源数据）
npm run audit:knowledge-trace -- --all

# 固定回归：索引语义、路径、快照与不能越级宣称的边界
npm run test:knowledge-lineage
```

状态是**本地结构追溯**，不联网校验远端blob、版权、原始研究结论，也不会记录用户隐私、改变模型权限或执行交易。

## 12. 下一轮怎样避免又陷入“搜索很多，能力没变”

对同一条实际任务沿**事实缺口**而不是新目录推动：
1. 若从最终结论找不回一笔具体原始事件/旧原文来源：先补来源与事件，而不是继续写专家理论。
2. 若同一知识在 blix 和PR23出现冲突：回共同祖先做三方比较，保留双方新增，再更新一次实际有效的位置，不使用简单覆盖。
3. 若明明有关键知识但AI漏选：固定自然语言问题，比较有无知识和不同路由，量化漏选/误用，再决定是否修改11个来源白名单。
4. 若代码能输出图谱但不知道经济身份：使用真实Mint做池/服务/Token-2022/SOL/WSOL/库存来源对照；当前图谱不能通过“知识修正”变成主网事实。
5. 若来源没有产品使用价值，但能产生重要新机制：留原 `references` 的来源/反证/开放研究，不强制转功能。若再查不会改变判断或可交付结果，就停止此分支。

**最终衡量**不是文档数、指标数、专家数或知识命中次数，而是从用户一句简单问题出发，能否沿 `结论→证据→来源→解释→适用边界→代码/测试→真实反馈` 双向复查，并能在新事实到来时**有依据地改变判断**。

**涉及外部来源的原始规范**：[ai-d 知识维护](https://github.com/sunshihao001/ai-d/blob/main/knowledge/foundations/organization-protocol.md)、[W3C PROV-O](https://www.w3.org/TR/prov-o/)、[OpenLineage 运行数据血缘](https://openlineage.io/docs/spec/facets/)、[Google skill-reach](https://google.github.io/skill-reach/)、[OpenAI Agent evals](https://developers.openai.com/api/docs/guides/agent-evals)。借鉴其关系和测试思想，不默认安装整套平台。
