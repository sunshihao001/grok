# 滚动式参考项目知识融合｜在 Grok 中把原 Meme 交易认知真正连接起来

> **当前采用的研究推进法**：**全局定方向、小批次滚动、每批走通“原资料理解→专家融合→Grok知识转换”，允许批次之间轻量并行**。这是现有 [专家机制研究法](expert-mechanism-research-method.md) 的执行节奏，不是新本体、新专家、新Bot或交易流程。
>
> 真实任务是把原 Hermes `sunshihao001/-`、策略理论 `meme-`、GMGN业务原型 `qb-` 与经审阅的外部研究，深化为 `grok` 的市场监控/钱包结构/跟单专业知识。保留 [原项目知识阶段审计](reference-projects-meme-knowledge-audit-20261030.md) 的边界；Why-Solana 的13个固定K1来源仍 `review_only`；不能把外部研究统计、旧平台标签或合成脚本执行结果升级为本地已核实的市场结论。

## 1｜为什么既不能全部串行，也不能全部并行

**全部串行的错误**：把参考库全量通读、改写成文档，才让专家研究，会使“资料迁移”无限延伸、先读知识容易忘、行业场景被剥离。最后每域看似都齐，但不知道为什么某类钱包值得研究。

**全部并行的错误**：Hermes同源、qb关键地址、meme的FCZ、外部发币首槽结论分别由多个AI同时扩写，若尚未明确相同名词的口径、时间和业务角色，会产生四套相互冲突却被并列进库的“专家知识”。

**应采用**：按**一个可复述的Meme市场问题**而不是一个仓库/一个学科划分研究小批次。每批同一组原始文档经过理解、融合和编译；上一个批次开始编译时，下一批可先做少量资料核查。这样不会因迁移整个仓库而迟迟没有专业产出。

## 2｜每个批次的实际执行协议

### A｜资料理解：先还原旧业务知识，禁止急于改写

每批先选约3–6份相互关联的**具体关键文件**，优先固定commit、文件路径、章节与术语原文的准确含义，不做整库无差别复制。用四个问题读：

- 当时研究/程序在**哪种Mint阶段和钱包行为**里使用这条知识？
- 这条知识究竟是原始事实、供应商派生字段、行为标签、结构推断、推演假说、待检验规则，还是实际运行证据？
- 它在旧项目里如何被计算、误解或降级？为何当时被认为有价值？
- 新Grok已有相同或相反知识吗？术语是同义、不同分母、不同时间窗口，还是经济含义不同？

**产物**：简短的原知识对照，至少包含“来源→原业务用途→事实/推断边界→当前Grok落点→待研究矛盾”。并非重写一篇宏观总结。若对某条文件未实际读取，不得标“已理解”。

### B｜专家融合：一轮只深入一条有意义的因果链

选一位现有21专家作为主专家，必要时找1–3位真正能提出不同经济解释的挑战专家（不必固定数量）。围绕明确矛盾，**向下追到钱包交易、Token/资金移动、库存/权限、发币阶段和报价；再向上推导参与者激励、市场行为、后续可见信息与跟单剩余价值**。

对同一个表象给出至少一个专业上不同的竞争世界，明确改变什么条件会使判断失效。不能只是枚举“可能是庄家/可能是散户”，也不能复制早期字段组合中的“极高概率”或未校准阈值。

**产物**：一份真正解释项目机制的专题/增量：旧认知哪里需要保留、哪里必须修正、新认识是什么、哪些反例存在、对其他领域有何影响。若未发现有力的新知识，应如实记录“暂无突破”，而不是造一套新名词。

### C｜Grok知识编译：已有知识必须能被正确调用

将审阅过的增量回填到现有 L0–L7、D01–D12、152个Dxx-Kxx条目和匹配的专家文件/ `registry.v1.json` 入口；保留原资料引用及争议。运行端只要能按问题找到精确的专家专业知识即可，**不必也不应该把三库全文一次塞入K0**。

**产物**：主专题+知识单元交叉链接+专家入口更新+来源状态+明确的“不能下什么结论”。只有需要具体程序支持时才考虑独立的只读测试/CLI适配，不因内容进入K1就部署Grok Bot。

### 复审条件

每批至少能回答：
1. 能追溯到原哪几份**实际阅读**的文件，能否指出与本项目不同的上下文？
2. 是否修复一处钱包/资金/筹码/时点/策略的具体逻辑断层，而不是换种表述？
3. 是否提出可解释的经济机制、竞争解释及其成立/失效条件？
4. 是否回填到现有专业知识入口，同时标出事实、假设与不可实证的部分？
5. 是否能说明对“监控什么、怎样理解、何时只能观察、不宜跟单”的实质增量？

**只有通过以上条件，才算这一批的“专业知识转换完成”；如果没有真实K2，不能顺带把预测或盈利阶段打勾。**

## 4｜并行容量：主研究一次只做一件事，其它工作不得占领认知

默认同时最多有：
- **1个主机制纵深研究**（例如B01的早期关键钱包）；
- **1个下一批资料溯源/字段核查**（例如B02提前检查Skill4的来源与字段，不开始独立大篇幅总结）；
- **上一个已审阅批次的少量知识入库/入口测试**（如果尚需收尾）。

三个环节可以**跨批次错位并行**，但同一个批次始终按“先准确理解→再专业融合→最后转换成可调用知识”推进。若有未解决的主要矛盾，不为了按进度“完成”而强行跳下一批。

不能“每个参考项目各起一个专家组同时写完”，也不以“每周必须N篇、N张卡、N个Bot”衡量研究。

**起点不是学会所有Token程序，而是旧qb关键地址矩阵中的一个问题**：

注意：上表是**已经核对的旧项目知识连接示意**，尚未完成其全部机制推导，更不代表真实钱包追踪或盈利验证已经完成。

## 6｜何时转下一批？

每轮收尾不是“单元填满”，而是判断：

- 这个项目问题能否被当前知识合理解释？
- 有没有新发现的主要矛盾要继续由主专家突破？
- 旧知识有何具体错误需要退回修改？
- 通过本轮，未来监控字段、窗口、行为角色或不应跟单条件是否更清楚？
- 下一轮用哪几份资料、哪一位专家和哪几个最相关原子单元就能接上？

若B01只发现“关键钱包不是确定赢家”这种旧结论，却没有深入不同钱包的经济权利/持仓与时差，则**继续B01**，不因为完成文字总结就进入B02。

**每次使用的最小记录**：当前具体问题→重用来源和文件/版本→取用哪项可观察机制→与另一种解释/方案对比→不采用及理由→本次结果（新增、修正、保持、暂停）→下一次什么条件再查。只写实际发生的研究差异，不要求每个来源每轮占一个章节。

**新增来源的入池条件**：能提供缺失的原始程序语义、可移植实现、现实失败模式、竞争解释、可得字段或可证伪新研究问题。保留 candidate/review_only 的状态；外部仓库的安装、权限、收费与动态安全变化需另行核查。

**方向复核**：本批方案是否直接服务“从链上经济事件→资金/库存/群体→异常解释→后续研判”；与旧项目方案和至少一个有意义的外部替代比较；若外部已成熟实现更好，允许明确 PIVOT。把搜索扩展作为发现未知的重要手段，但不能让文献/新工具数量取代实际进度。


## 7｜与工程线及来源权限的分离

本方法是当前 `knowledge/system/mechanism-research-plan.v1.json` 的**执行节奏**。GPT理论研究与知识编译可以滚动推进；`docs/next-steps.md` 的Grok S1云端固定SHA验收、S2真实只读源、K2/策略实证是另一套运行交付阶段。

读外部Why-Solana仅限原source-admission许可的专项审阅，独立统计仍需另行核查；不会因B05引用而默认授权给Grok。对旧 qb- 的文件路径与程序名称保留原始版本，不能声称旧GMGN付费CLI目前已在Grok中可运行。

**一句话规则**：一批 = 一个具体Meme交易问题 + 少量原始资料 + 一个主专家的深入经济解释 + 竞争机制 + 原单元回填。主研究聚焦，资料核查和前批编译有限并行；内容成熟后才进入可调用专家知识。
