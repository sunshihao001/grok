# GPT × GitHub｜Solana Meme 知识层级累积、双向关联与持续修订规范 V1.0

> 目的：解决“研究分散在多轮聊天、每次只知道某一点、忘掉其他领域、无证据自我升级、GitHub与GPT项目观点不一致”的问题。本规范是现有 `gpt-meme-project-core.v1.md` 的增量机制，不是另一个知识本体，也不改变F0–F6、K0/K1/K2或Grok运行授权。

## 一、每一条有价值知识到底要保存什么？

**不只保存结论；保存它从哪里来、为什么成立、改变了哪条市场认知、会在哪些条件下失效。**

一次研究的最小保存记录可按如下Markdown模板，字段缺失时允许注明“未知”，不能靠模型猜测填满：

```markdown
# MECH-<现有批次>-<主题>｜有市场意义的知识增量
- 当前研究目标与原话：
- 研究市场对象：Mint / 钱包 / 群体 / 交易/资金边 / 发币阶段 / 时段：
- 分类归属：主 Dxx-Kxx；影响 Dxx-Kxx（不改原编号）
- 主专家/挑战专家：现有 E-Lx-xx
- 原项目知识入口：仓库+固定提交+路径/章节；来源准入/引用限制
- 原先认识是什么：被替代/被约束的推断，或目前未知
- 直接事实（何时、何值、源头）：记录事件时点与数据可得时点，没K2写“无”
- 经济机制：主体、权利、资产、交易、库存、价格和激励怎样共同作用
- 不同的竞争解释：至少一个能产生同样表象的世界
- 反证与条件反转：什么观察或条件变化会推翻/缩小此解释
- 对监控的作用：需要观察什么时段、事件、钱包子群、字段/来源
- 对跟单的含义：仅解释 / 预警 / 发现 / 风险排除 / 需独立验证的交易候选
- 新问题：下一处最重要未知及为什么
- 证据状态：来源理解/理论推导/外部报告/本地实证（分开）
- 变更：新增、修订、撤回、归档；修订原因与上一版引用
- 项目镜像：GitHub路径、commit、GPT Project附件镜像版本
```

**进度不可混为一谈**：

- **目录覆盖**：已有152个单元，说明什么问题值得研究，不代表被研究；
- **原知识理解**：确实阅读过原文/源码，能准确解释上下文、局限与相反解释；
- **机制深化**：能从交易/资金/库存等原语推导市场经济后果，形成经审阅的条件化解释；
- **独立实证**：有真实K2、能重建的分母/时点/基准/成本，在相应F关卡审阅；
- **运行交付**：实际程序/数据与Grok云电脑验收，是另一条独立进度。

机制理解的成熟不等于盈利证据成熟；不要给一个总“知识成熟度分数”覆盖这些区别。

## 二、层级回填规则：一条发现到底放哪儿？

**第1层：用户真实研究问题和当前批次**。保存其业务意义，保留“不跟单也可以有监控价值”的研究空间。例如：在某10秒窗口很多钱包批量转账，为什么？

**第2层：当前Mint/钱包/事件的事实语义**。读D01/D02/D10，先分辨是否为真实链上转账、swap、程序CPI、路由/池内动作和不同来源事件；事后推断和实时可见分开。

**第3层：专业角色与经济机制**。把该事件连接D04钱包角色、D05资本/公共服务、D06自由可卖库存、D07时间与共因，必要时D03池价/LP。

**第4层：跨域因果关系和竞争世界**。原始转账数较多可能是统一资金分发、普通公开事件引起的并发、第三方机器人服务、LP路由活动或真实多主体活动；每条世界必须给可区分条件，而不是写成“也有可能”。

**第5层：面向监控与策略知识的含义**。D08可产生新监控特征、研究发现或风险过滤候选；D09计算在信号可得时是否还有实际双向成交条件；D11检验零假设、时间泄露、负对照，不把“异常”直接当“优势”。

**第6层：保存、复用、追踪**。将主专题保留为完整解释链，把受影响的原Dxx-Kxx/专家入口记录成跨域链接，保存矛盾和未完任务；GitHub审阅后做GPT Project同版本镜像。

这里的“第1–6层”只是**一个研究结果由问题走向知识资产的说明顺序**，**不是取代现有L0–L7的第九套层级**；不同问题可以直接从第3层进入、反向追至第1层。

## 三、必须建立“有类型的关系边”，防止词条孤立

建议关系采用稳定、少量、能说明市场意义的动词，**相关不等于因果**：

| 边 | 含义 | Meme项目实例 |
|---|---|---|
| `is_part_of` | 归属完整机制 | D05-K02是“关键钱包经济职责”机制的一部分 |
| `requires` | 若要成立必须依赖 | “可复制首买优势”要求信号时点早于仍可获利的成交机会 |
| `explains` | 在条件内解释现象 | 钱包转入/转出和资金闭环解释部分异常活跃 |
| `challenges` | 提出竞争解释 | 公共HUB挑战“相同上游资金即同控” |
| `conditions` | 成立范围或反转条件 | LP增加可改变同额Token卖出的池价冲击 |
| `informs` | 改变下游研究问题 | 早期同源群库存下降提示检查D09卖出可得流动性 |
| `supersedes` | 经审阅替换旧推断 | 具体“实际卖出”证据替换旧的“Token转出=卖出”表述 |
| `contradicts` | 两来源/模型冲突，待审 | 供应商同一个bundle字段在不同版本定义冲突 |
| `opens_question` | 生成未解的新研究 | 统一补款后的钱包群是否在下一Mint被复用 |

**边需要附条件**：关系的两端ID、关系类型、具体市场机制原因、适用Mint/阶段/时段、原始来源、目前验证状态、记录版本。禁止直接按共现把两个词之间连成“支持”。

## 四、当前项目最重要的一条完整累积示例：批量异常钱包转账

用户启发：**不同时间段、批量异常钱包转账的数量不同，这可能比单钱包标签更有用。**

1. **要观察的不是单一数字**。定义窗口内“出现的地址数”“真实外层转账次数”“归并后经济主体的候选数”“Token实际净流入/净流出”“进入/退出的Mint数”。重复地址同一个窗口与跨窗口分别计数。分母可以是同龄新币、同市场活跃度、同供应商覆盖，而不是所有时间里的原始笔数。
2. **明确窗口不是结论**。1/5/15秒、1/5分钟可作为探索候选；窗口是感知尺度，非已验证阈值。创建slot、曲线毕业、Dev动作、KOL推送会改变正常基线。必须保留零活动窗口及没有后续拉升的样本。
3. **钱包类型必须分清**。同时间有30个转账地址，可能只有少数资金组织节点+多路执行子钱包；也可能是大量独立买家；或是DEX/路由内部账户。候选归并带不确定性，不能把地址数直接当真人数。
4. **改变哪些经济关系**。发现共同出资→D05；接收者随后将Token卖入池→D06与D03；只转仓不卖→库存位置变化、池价不一定变化；多个Mint重复出现同一角色→D07资本轮动研究。
5. **怎样形成可用监控思路**。可监控按群体/阶段分层的“突发数量、净金额、接收后到swap的时间间隔、同源组剩余仓位变化、重复Mint参与、与正常基线差异”。这仍只是候选发现手段，未有真实数据验证。
6. **研究下一个未知**。如果钱包群到达池前会批量转账，是否能从这个前兆获得比普通公开价格与成交量更早的信息？或只是公共事件/服务机器人？是否在当时可以读取？这才是D08研究题。
7. **知识回填**。主机制 `knowledge/domain/` 独立专题，引用D07-K08（异常序列）、D05-K02/K03/K06（资金与复用）、D06-K07/K09（库存与派发）、D01-K07（真实交易语义）、D10-K05（时间可得）、D11-K03/K04（竞争解释/冻结时点）；不必为每个交集重新建章节或新领域。

从一句实际监控灵感出发，得到一条能被多个专家理解和继续深入的机制，而不是增加一个“转账异常分数”。

## 五、一个专门防止知识零散的“每轮收工”检查

**只有值得长期复用的内容才写入正式知识**；一时猜想可保留在开放问题/研究工作稿中。每轮至少检查：

- 是否写清原研究问题与**项目的具体Meme业务场景**，不是泛用金融学定义？
- 原来源中哪些结论已经存在？现在真正新增的是哪一条机制、边界或反例？
- 横向关联了哪些已有Dxx-Kxx与专家？每条连接为何成立，是否有可能是共因？
- 失败或新反例会不会推翻旧内容？旧内容被修订后还能否回查？
- 是否只写了“可能有庄家、需要验证”，没有解释资产/库存/时序/利益变化？
- 研究的产出究竟提高了**识别、解释、预测还是经济执行**的哪一种能力？不能混称。
- 是否在GitHub固定来源与PR审核？GPT Project附件是否与当前commit对应？不一致就报漂移。

如果只是“多写了3页总结”而没有新认识，不能把该批次标完成。**允许没有新突破**，只要如实记录究竟卡在哪个实质性未知。

## 六、GPT Project内长期工作：不依靠聊天自动记忆

GPT的Project文件和个人Library是可保存的外部资料，不等于模型永久记住所有旧聊天。每个新专题应通过项目核心镜像、源索引、当前进度与相关专题恢复状态，不要依赖“你记得上一轮”这一假设。

**GitHub为主真源**：新的完整专业内容在对应Draft PR版本化；GPT Project镜像由该版本生成。用户明确在GPT项目附件中更新之后，新会话才有明确对应的镜像资料。**我们目前没有可直接替用户把文件附加到这个Project的工具，因此不能声称已自动附加或同步**。

**两侧职责**：GPT是构思、专家机制推演、跨域整合和审阅工作台；GitHub是知识与源码版本真源；Grok是待验收的只读运行端。形成知识只意味着将来有可读材料，不能自动使Grok理解或运行，也不能自动批准金融交易。

## 来源准入：外部研究不可因知识图连接而变成事实

本项目 `knowledge/source-admission.v1.json` 中，Why-Solana研究相关固定来源目前仍为 `review_only`。可以在专项来源审查中吸收其失败模式和研究问题，但不能自动当作本地已复算的K2证据，不能因别的专家引用就提升其准入权限。旧Hermes/`meme-`/`qb-`中的示例分数同样不能自动成为真实行情结论。

**本文批量钱包示例涉及的完整原子映射**：`D07-K08` 异常序列、`D05-K02`风险本金/执行服务、`D05-K03`公共HUB排除、`D05-K06`跨Mint资金复用、`D06-K07`早期库存、`D06-K09`真实转仓/成交/派发、`D01-K07`指令语义、`D10-K05`观察可得时间、`D11-K03`竞争机制、`D11-K04`时点冻结。**仅映射到这些条目并不意味着完成实证或该条目升级。**

## 七、首批B01应怎样累积而非仅写研究计划？

在已读 `qb-/sikk_gmgn_token_report.py`、Hermes `learning/10.md`、`learning/11.md` 和当前Grok的D05经济职责文档之间建立原始知识对照。之后应由E-L4-02和E-L3-01/02/03把 `holders_smart`、`holders_bundler`、`holders_transfer` 的**不同经济角色、真实库存与可见时间**真正推导清楚，优先找旧标签失效的反例。专题通过理论机制复核后再回填原单元，市场盈利仍须独立验证。
