## 1. 真正需要组织的不是“更多模块”，而是五种不同职责

```text
[用户自然语言 / 未来Grok命令]
         │     用户意图、研究目标、查看/监控/核查要求
         ▼
[任务组织与交互] ─── 知识导航短名单 ───> [现有专业知识]
         │          (只返回路径)           D01-D12 / 152问题
         │                                   22专家视角/原专题
         │                                   65资产/来源与反例
         ▼
[现有业务功能] ──────────────────────────────────┐
 Mint报告 | 钱包候选 | 资金关系 | 异动窗口       │ 只有真的接通的
         │                                      │ 功能可调用
         ▼                                      ▼
[来源/事件与证据]  <──────────────── [原始供应商/链上来源]
 DEX Screener/RugCheck现有真实供应商报告
 Million/OKX/外部SDK仍依安全/授权/数据条件
         │
         ▼

```

上图描述关系，不表示已存在一个完整的运行时调度器。尤其机器导航程序只读索引，不能直接调用工程PR #16里的模块。

## 3. 业务数据与认知知识不能共用“已验证”标签

- **Raw source**：来自哪一个供应商/哪条链上交易？原响应、哈希、查询时间。
- **Normalized observation**：金额、Token账户/Owner、event_at/available_at、覆盖完整性；转换错误显式报告。
- **Claim / mechanism**：可能由哪些经济机制生成；竞争解释和缺证；受什么知识文档支持。
- **UI report**：将观察和解释并排展示，绝不把推论当作原始事实或把模型判断回写供应商原始数据。
- **Monitoring state**：断线、限额、重复事件、重启、版本升级单独记录；不能用没有新事件代替缺源失败。

**关系图特殊限制**：边只能表示具体可观察的钱包/Token/资金连接，控制权与协同意图是额外推论。跨多钱包同交易签名既不能漏记涉及的钱包，也不能把同一Swap累加为多笔经济成交。未完成这类语义验证时，NETWORK与ALERTS仍只能标未验。

## 4. 跨分支管理和真源优先级

- 知识分支：`knowledge/whole-spectrum-20261030-v1`，Draft PR #14，研究体系和本次UI/导航设计。
- 工程分支：`research/p24-cross-mint-m01-batch-monitor-20261031`，Draft PR #16，真实Mint/报告/离线监控和工程证据。
- `main` **不自动包含两个Draft分支的组合**。相同路径在不同分支可能代表不同版本。
- 多个知识索引**不是重复数据库**：152个问题（scope）与22个专家（lens）、65项资产（candidate）和21条K1来源（retrieval index）用途不同，不应合成一个没有语义的统一ID表。
- 若将来需要真正统一导航与业务运行，必须创建可审查的集成分支，核对冲突、执行测试/真实数据验收后再合并；不允许为了“文件夹好看”直接搬动和重命名已有知识文件。

## 5. 容易被遗漏的工程/产品问题（本轮提前纳入规划）

| 问题 | 后果 | 应采用的措施 |
|---|---|---|
| 文档存在但 AI 路由不到 | 长期知识不发挥作用 | 用多意图真实问题做路由召回检查，漏路由时补关联而不是复制正文 |
| 关键词匹配误导专业推理 | 错领域、重复加载过多上下文 | 路由只给候选，模型必须按上下文判断；遇到未知继续探索关联领域 |
| 研究文档与工程PR不一致 | 把fixture功能说成实盘可用 | 工程能力引用分支、文件、实测记录，单独标状态 |
| 外部SDK及供应商限制 | 成本失控、密钥/交易风险、失效 | 检查许可证、启动副作用、只读权限、潜在自动付款、调用额度和限流 |
| 账户身份/资产时钟错误 | 把AMM、共享服务、Token账户误认自然人/庄家 | 保存TokenAccount/Owner/程序角色、真实时点、竞争解释与UNKNOWN |
| 定时监控漏数与重复计数 | 假异常或漏报 | 事件去重维度、窗口覆盖、重启恢复、断流报告；先实证后上线 |
| 模型长期知识污染 | 旧推论和新实测冲突 | 保存结论出处、版本、退役原因；只有有证据时更新权威专题 |
| 单轮文档暴涨 | 降低推理可用上下文 | “索引引用→选择性读取→专业推理”而非每轮加载152单元全文 |
| 界面过度先行 | 做出漂亮但无数据的空壳 | 首版优先现有Markdown/JSON，资金与告警真实后再开发图形/推送 |
| 实际运行不可重现 | 出现问题无法排查或恢复 | 固定SHA、源JSON/哈希、依赖、日志、错误状态与环境；Grok真实云端单独验收 |

## 6. 下一步怎样实际验收“AI能正确调用知识”

这不等于再办一次框架设计研讨。直接做小型评测：

1. 从已有用户问题中抽10–20个不同意图的自然表达，包含模糊/错误前提、跨域问题、仅研究不开发和工程故障。
2. AI先用机器导航及原始专题作答；检查是否引用正确的真实文件和专业机制，是否错误承诺未实现能力。
3. 对照没有导航时的结果，以**相关内容召回、错误引用、知识冲突、误归因、任务完成率、额外读取成本**评价。评测集应有人工审查参考答案，不能让同一模型仅凭自评宣布提升。
4. 将确认的遗漏修回本索引或原研究专题，不创建与本体竞争的新分类。
5. 对产品缺口继续按实际可用数据推进，不要求专业研究一定服务当轮开发；两个方向可独立深化并互相反馈。

**当前交付边界**：信息架构、UI规格和静态知识导航有明确设计；统一实际Grok调用和用户可交互前端仍待工程集成与运行验证。
