## 1. 真正需要组织的不是“更多模块”，而是五种不同职责

```text
[用户自然语言 / 未来Grok命令]
         │     用户意图、研究目标、查看/监控/核查要求
         ▼
[任务组织与交互] ─── 知识导航短名单 ───> [现有专业知识]
         │          (只返回路径)           D01-D12 / 152问题
         │                                   22专家视角/原专题
         │                                   65资产/来源与反例
         ▼
[现有业务功能] ──────────────────────────────────┐
 Mint报告 | 钱包候选 | 资金关系 | 异动窗口       │ 只有真的接通的
         │                                      │ 功能可调用
         ▼                                      ▼
[来源/事件与证据]  <──────────────── [原始供应商/链上来源]
 DEX Screener/RugCheck现有真实供应商报告
 Million/OKX/外部SDK仍依安全/授权/数据条件
         │
         ▼

```

上图描述关系，不表示已存在一个完整的运行时调度器。尤其机器导航程序只读索引，不能直接调用工程PR #16里的模块。

## 3. 业务数据与认知知识不能共用“已验证”标签

- **Raw source**：来自哪一个供应商/哪条链上交易？原响应、哈希、查询时间。
- **Normalized observation**：金额、Token账户/Owner、event_at/available_at、覆盖完整性；转换错误显式报告。
- **Claim / mechanism**：可能由哪些经济机制生成；竞争解释和缺证；受什么知识文档支持。
- **UI report**：将观察和解释并排展示，绝不把推论当作原始事实或把模型判断回写供应商原始数据。
- **Monitoring state**：断线、限额、重复事件、重启、版本升级单独记录；不能用没有新事件代替缺源失败。

**关系图特殊限制**：边只能表示具体可观察的钱包/Token/资金连接，控制权与协同意图是额外推论。跨多钱包同交易签名既不能漏记涉及的钱包，也不能把同一Swap累加为多笔经济成交。未完成这类语义验证时，NETWORK与ALERTS仍只能标未验。

## 4. 跨分支管理和真源优先级

- 知识分支：`knowledge/whole-spectrum-20261030-v1`，Draft PR #14，研究体系和本次UI/导航设计。
- 工程分支：`research/p24-cross-mint-m01-batch-monitor-20261031`，Draft PR #16，真实Mint/报告/离线监控和工程证据。
- `main` **不自动包含两个Draft分支的组合**。相同路径在不同分支可能代表不同版本。
- 多个知识索引**不是重复数据库**：152个问题（scope）与22个专家（lens）、65项资产（candidate）和21条K1来源（retrieval index）用途不同，不应合成一个没有语义的统一ID表。
- 若将来需要真正统一导航与业务运行，必须创建可审查的集成分支，核对冲突、执行测试/真实数据验收后再合并；不允许为了“文件夹好看”直接搬动和重命名已有知识文件。

## 5. 容易被遗漏的工程/产品问题（本轮提前纳入规划）

| 问题 | 后果 | 应采用的措施 |
|---|---|---|
| 文档存在但 AI 路由不到 | 长期知识不发挥作用 | 用多意图真实问题做路由召回检查，漏路由时补关联而不是复制正文 |
| 关键词匹配误导专业推理 | 错领域、重复加载过多上下文 | 路由只给候选，模型必须按上下文判断；遇到未知继续探索关联领域 |
| 研究文档与工程PR不一致 | 把fixture功能说成实盘可用 | 工程能力引用分支、文件、实测记录，单独标状态 |
| 外部SDK及供应商限制 | 成本失控、密钥/交易风险、失效 | 检查许可证、启动副作用、只读权限、潜在自动付款、调用额度和限流 |
| 账户身份/资产时钟错误 | 把AMM、共享服务、Token账户误认自然人/庄家 | 保存TokenAccount/Owner/程序角色、真实时点、竞争解释与UNKNOWN |
| 定时监控漏数与重复计数 | 假异常或漏报 | 事件去重维度、窗口覆盖、重启恢复、断流报告；先实证后上线 |
| 模型长期知识污染 | 旧推论和新实测冲突 | 保存结论出处、版本、退役原因；只有有证据时更新权威专题 |
| 单轮文档暴涨 | 降低推理可用上下文 | “索引引用→选择性读取→专业推理”而非每轮加载152单元全文 |
| 界面过度先行 | 做出漂亮但无数据的空壳 | 首版优先现有Markdown/JSON，资金与告警真实后再开发图形/推送 |
| 实际运行不可重现 | 出现问题无法排查或恢复 | 固定SHA、源JSON/哈希、依赖、日志、错误状态与环境；Grok真实云端单独验收 |

## 6. 下一步怎样实际验收“AI能正确调用知识”

这不等于再办一次框架设计研讨。直接做小型评测：

1. 从已有用户问题中抽10–20个不同意图的自然表达，包含模糊/错误前提、跨域问题、仅研究不开发和工程故障。
2. AI先用机器导航及原始专题作答；检查是否引用正确的真实文件和专业机制，是否错误承诺未实现能力。
3. 对照没有导航时的结果，以**相关内容召回、错误引用、知识冲突、误归因、任务完成率、额外读取成本**评价。评测集应有人工审查参考答案，不能让同一模型仅凭自评宣布提升。
4. 将确认的遗漏修回本索引或原研究专题，不创建与本体竞争的新分类。
5. 对产品缺口继续按实际可用数据推进，不要求专业研究一定服务当轮开发；两个方向可独立深化并互相反馈。

**当前交付边界**：信息架构、UI规格和静态知识导航有明确设计；统一实际Grok调用和用户可交互前端仍待工程集成与运行验证。

## 7. 全项目多层计划：覆盖全面，执行自适应（2026-11-01 增补）

### 7.1 先明确“梳理完成”到底指什么

本轮此前已经完成的是 **资产发现、静态知识导航、UI信息架构的初稿与离线测试**；不能据此宣布“全量研究知识都已正确关联、AI已能理解和调用、产品UI已集成”。“梳理完成”要分别成立：

| 层级 | 要回答的关键问题 | 已有成果（截至本次增补） | 尚缺的可检查验收 |
|---|---|---|---|
| ① 目标和产品边界 | 用户到底想通过哪类问题得到什么结果？ | `design/product-experience-architecture.v1.md`、PR #16 V0.1报告目标 | 用含糊自然语言和真实使用情境核对用户旅程；不把UI设计稿当成上线 |
| ② 资产和知识归位 | 哪份文件权威、属于哪一层、哪些只是旧版？ | 12域、152问题、22专家、65项参考、K1索引、旧知识卡已区分 | 审读不同入口的冲突/空缺/重复引用，逐个给出“保留原文、修正链接、退役错误指令”的裁决；不删除学术和业务知识 |
| ③ 知识选择与跨域关联 | 简单表达能否找到**真正适用**的旧知识，并发现未被提到的关键机制？ | 13个任务路由及可读原文件片段的CLI，静态ID/路径测试 | 使用用户真实问题集做路由召回、误匹配、反例、知识关联、无匹配的扩展能力评测；与无导航基线比较，检查原文是否真的被读到 |
| ④ 工具和业务功能调用 | 知识建议与现有源码/服务是否准确衔接？ | PR #16 V0.1真供应商报告，钱包批量算法仅离线 | 对每个产品能力查**哪个分支、哪个入口、真实依赖、原始I/O、许可、成本、安全、失败输出**；实际同输入端到端验收，避免“参考源码存在”冒充“调用成功” |
| ⑤ UI和产品交互 | 用户能否看懂结论、来源、未知、失败、下一步？ | 7个视图的文本UX规格；现有Markdown/JSON报告 | 用真实V0.1报告核对每个区块的数据映射、Mobile/Grok聊天摘要、缺失与错误显示；未来网络/告警无实数据时显示未实现 |
| ⑥ 运行和持续质量 | 新任务、新来源、新代码出现后，怎么保持知识和成品一致？ | GitHub PR、离线CI及来源/版本规范 | PR #14与#16集成测试、Grok实际调用与错误恢复、重复/断流测试；来源/指针漂移回归、定期人工审阅反例，才可能稳定运行 |

上述六层是**完整性检查维度，不是强制串行的P1–P6阶段，也不是六套子系统**。一个任务可能同时推进多层；是否继续取决于能否明显改变知识正确性、功能完整性或用户结果。

### 7.3 真正的持续推进机制：维护一条“有证据的工作队列”，不强制固定提示词

每次用户说“继续”时，AI应该：

1. **恢复**：读取这份计划、PR #14/#16 的当前代码和必要证据，只读取与任务有关的原知识，不机械灌入全库。
2. **识别断点**：比较用户最终能得到的结果与实际能力，找出最影响可靠性/可用性的1–3个缺口；检查是否已经有现成实现可复用。
3. **独立决策**：考虑信息价值、依赖、实测成本、风险和可能的误判，选最有收益且在权限范围内的一项工作。可直接研究专业机制，也可执行代码/UI/导航/测试；必要时重新排序。
4. **立即执行并核查**：不止停留在报告；修改已存在的原文或代码、运行测试/回读GitHub，保留真实引用、提交SHA、错误和剩余未知。若因权限/外部费用受阻，诚实标注并选下一项安全可做的工作。
5. **轻量交接**：只在有真正进展时更新已有文档中的状态/验收；给出“实际做了什么、证明到哪一级、仍差什么、下一项建议”。无需每轮生成新版本、固定大段汇报和复制提示词。

**进度状态应细分**：`INVENTORIED`（登记）→`LINKED`（关联）→`SOURCE_READ`（原文核读）→`STATIC_TESTED`（结构/代码离线测试）→`REAL_DATA_TESTED`（真实数据）→`GROK_VERIFIED`（云环境实际运行）。这只是证据级别的示意，**不是单一线性晋级规则**：知识研究可有强理论但无程序，UI可有完整设计但无真实资金图。不同能力分别记录，不许偷换“已完成”的意义。

**停止条件**：当前用户目标得到可核验交付；或新增信息预期不足以改变判断；或遇到权限/安全/成本硬约束。停止当轮不代表永久停掉知识研究。

### 7.4 优先验证的真实断点（不要再新建一个平行框架）

- **A｜知识真的能用吗？** 先对现有导航做15–20个自然语言题的人工标准评测，混入模糊、跨领域、错误前提、纯研究问题；判定读到的原文是否准确、是否遗漏相关旧知识。无导航基线对照，不用模型自评冒充提升。
- **B｜能力真的能调用吗？** 选一个真实V0.1 Mint场景，核实报告字段→UI区块→相关知识解释→原来源的闭环。随后以实际需要、许可和数据源情况推进V0.2真实关系；不能拿合成网络图代替实际关系。
- **C｜两个PR真的兼容吗？** 明确PR #14里的导航/知识代码与PR #16真实Mint程序在不同分支，先检查共同基线和接口差异，在受控集成候选上跑测试；没有安全审查不合并主分支。
- **D｜Grok真的能复用吗？** 在可用授权环境验证自然语言→正确程序→报告与知识引用→错误反馈→再次查询；不把脚本/Markdown说明当作已部署Bot。

初始可先推进A，同时若A不阻塞B，可在工程侧独立推进B；C/D需要相应依赖满足。实际证据出现后允许改变优先级。

### 7.5 用户未来只需一条续接表达（随时可缩短）

> **继续 Solana Meme/Grok 项目的全局梳理与真实整合。保留并主动运用全部已有专业研究、源码和参考项目；以当前两个PR、UI设计、知识导航及实际测试为基线。你负责识别最重要的知识调用、跨域关联、产品设计或工程集成断点，依据证据自主选择最有价值的工作，先复用再修改，实际执行、测试和回读。持续修正遗漏与错误，但不要重建知识框架、机械扩建专家体系或重复制定计划。说明已证成果、未证部分及下次最值得解决的实际问题。**

更短的表达也同样有效：**“继续这个项目。先核对现状，选择当前最重要的实际断点，执行并验收；保留已有研究知识，不重复造框架。”**

这是一条**恢复意图的输入**，不是模型必须遵循的封闭流程；实际任务、关键未知和新证据优先于提示词模板。

## 8. 跨分支实际整合成果与仍存在的系统缺口（2026-11-01）
