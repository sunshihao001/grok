# Solana Meme｜目标演化与 AI 自主职责：现行决策记录（2026-11-05）

> **定位：可修订的业务决策记录，不是新增的知识本体、Agent 框架或自动调度器。**
> 依据：用户从早期跟单研究到现在的目标表达；当前 [执行准则](../knowledge/system/current-operating-guidance.md)、[产品体验](product-experience-architecture.v1.md)、[工程证据](../docs/evidence/v01-real-rugcheck-holder-2026-11-01.md)。其中“用户曾表达什么”按对话历史记录，“何种变化更有价值”属于 AI 当前判断；两者不可混淆。

## 1. 先分清目的、战略、产品、手段、任务

| 关系层（非技术 ID） | 现行内容 | 谁可以改变 | 何为有效结果 |
|---|---|---|---|
| 长期价值与人的目的 | 提高对真实市场的理解；识别经证据支持的机会、风险和经济机制；尽量减轻用户专业技术负担。是否追求收益、愿承担多少风险由用户决定 | AI 研究并建议，用户决定 | 用户认为有用，证据可复查，成本和风险真实透明 |
| 长期战略 | 建设能够不断学习并持续提升的 **Solana Meme 市场智能产品**，非单纯跟单/标签/信号器 | AI 可主动提议扩展或修订，重大变化由用户选择 | 形成有持续利用价值的市场发现与调查能力 |
| 产品业务 | 市场发现 → 单 Mint 关键钱包/Creator/资金/库存调查 → 跨 Mint 群体变化监控 → 机制研究和机会评估 | AI 根据现实证据主动设计与优化 | 同一用户任务可从输入走到可解释、可复查的输出 |
| 交付战略/资源 | 优先整用或有限修改成熟成品；Blix 第一候选，Pulse 保留对照，Million、PumpTrace、HoldTech、OKX 等按需复用 | AI 可比较并在已有授权内调整可逆实现；重大预算/重构需批准 | 少造轮子，更快取得可靠可运行成果 |
| 具体执行 | 以已有真实 Mint 样例进行主体对照；调查钱包、资金来源和多池数据语义；测试恢复与只读隔离 | AI 主动执行、验证并纠错；外部高风险动作须审批 | 实际运行证据、测试结果、代码和可打开的产品 |

注意：原知识体系中的 L0–L7 是**专业知识层**，不是本表的“目标层”，不要相互改号或强制对齐。

## 2. 真实目标如何演化：不是不断叠加任务

| 历史表达/转折 | 从中识别的真实问题 | 当前归位 | 是否还应该驱动默认开发 |
|---|---|---|---|
| 找值得跟单、能赚钱的钱包 | 希望找到有价值且可能复制的市场机会 | **仍然有效的应用目标**，不是项目全部 | 不能以只做钱包排名覆盖其他能力；不能把历史收益当可跟性 |
| 为什么钱包能盈利、如何研究开发者 | 需要了解资金、库存、交易和经济机制 | **专业调查与机制研究** | 有关问题应继续按需深入 |
| 批量地址转账、协同、隐藏关联、跨币群体 | 需要从单地址转向动态市场组织 | **市场调查和持续监控业务** | 是现行重要业务，不默认归因为庄家 |
| 跟单只是小领域 | 战略由“复制别人交易”扩展至市场事实、组织与价格形成 | **长期战略已扩展** | 不再把所有研究压成跟单信号 |
| 构建大量知识、12域、专家和长期记忆 | 避免遗忘、提高专业研究深度和复用 | **重要资产与研究方法**，不是交付前置工作 | 不再机械全库载入、全专家运行或逐阶段完成 |
| Grok Bot、命令中心、多 Bot | 用户希望简短表达，AI 承担专业执行 | **可能的交互与运行手段**，非永久架构 | 仅当真实可用且改善结果时采用 |
| 研究 Million、Pulse、Blix 等成品 | 不想重复造轮子，尽快运行完整业务 | **当前交付策略** | 需要现实测试；不能因某一局部缺陷马上放弃成熟成品 |
| 旧规则使 AI 变僵化、只输出不执行 | 方法开始阻碍目标 | **协作方式修正** | 旧知识保留，固定操作规则退役 |
| 每轮成果后还要发现更好的目标/想法 | 静态目标和下一步模板不足 | **主动再推演能力** | 依据新增证据筛选新目标，不为发散而无限重规划 |
| 最新要求：除人应做的外尽可能交给 AI | 需要跨层目标管理及端到端责任承担 | **当前人机协作原则** | 既扩大自主执行，也保留人类重大方向和权限控制 |

### 目标变动时的判断

一次新的简短输入，可能是：**目标细化**（增加条件）、**业务扩展**（加入新场景）、**战略替代**（旧路线不再合适）、**方法改变**（用成熟成品代替自建）、**纠错**（旧答案/旧目标错误）、**探索性想法**（尚不应直接替代战略）。

AI 应先判断其性质与上层目标的联系，指出收益和代价；不把“新想法”自动添加为第 N 个永久模块。能共存的保留，冲突的明确比较；旧证据和工作成果始终可追溯。

## 3. AI 的责任全覆盖，不等于创建对应数量的 Bot

| AI 自主承担的责任 | 当前项目中的实际表现 | 验收证据 |
|---|---|---|
| 目标识别与升级 | 从“找钱包”识别可跟性/真实经济机制/市场发现等不同层次 | 不把方法当最终目的；能解释变化 |
| 主动找未知与新目标 | 注意群体成员变化、数据覆盖、错误归因、跨币资本循环和新的成熟成品 | 新方向有可证伪问题和现实意义 |
| 知识选择与深研 | 按实际问题选择 Hermes/qb-/meme-、D01–D12、参考项目的源码/测试/设计历史 | 读原文而非只匹配关键词；指出边界和反例 |
| 多路径选择与取舍 | 比较整用 Blix / Pulse、薄集成、替代方案及不做的机会成本 | 说明推荐、反对意见、推翻条件 |
| 产品体验与业务设计 | 用户简单命令→Mint/钱包/资金证据→调查报告→持续观察 | 明确显示来源、失败、UNKNOWN、可追问 |
| 数据与专业工程 | Token Account/owner、签名/事件序号、SOL/WSOL、多池、历史缺口和错误时间窗 | 原始输入、转换、去重和负例测试 |
| 编码、集成、质量和安全 | 实际修改、审查依赖、只读隔离、单测、集成测试、日志、恢复 | 提交/可复跑结果，不能只写计划 |
| 监控/资源与停止判断 | API 配额、费用、故障、成本收益、停止低价值调查 | 不超预算，报告不可用状态及取舍 |
| 独立反证与自纠 | 用竞争机制、反例和失败数据挑战自己的解释和方案 | 不将供应商标签当因果，允许撤销结论 |
| 长期状态与成果恢复 | 对照 PR #14/#16/#17、现成程序、最新真实执行、历史问题 | 不重复早已完成的任务；每轮可核实进度 |
| 每轮结束后二次思考 | 判断新证据是否应该改变目标、战略、产品或具体下一步 | 末尾列出真正值得考虑的方向和首选，或明确没有新路线 |

以上是**责任清单**而不是强制流程。某项任务只需相关责任发挥作用，不要求每次逐行汇报。

## 4. 用户必须保留的职责与介入时刻

- 由用户确认自身最终目的、可接受的风险与资源、重大产品战略取舍，以及何时停止或改做别的目标。
- 私钥、交易/签名、自动支付、外部发布、账户/云端权限扩大、不可逆删除等，必须由适当权限主体在明确批准和安全条件下操作；本项目当前 **只读**。
- AI 可主动推荐与准备方案，不将“用户尚未知道自己该问什么”视作用户失职。
- 一般可逆且在授权范围内的研究、文档、测试和功能开发由 AI 主动推进并复核，避免把细小的技术选择不断交还用户。

## 5. 本轮对现状的实际裁决（截至 2026-11-05）

**当前不是重新规划架构，而是让目标演化直接改善产品选择。**

- **已验证：** PR #16 的 2026-11-01 GitHub Actions 对一枚真实 Mint 取得 DEX Screener 的 5 个池、RugCheck 缓存的 20 条 Holder Token Account 候选与 Creator 候选；跨源地址相等识别出一条 AMM 基础设施候选。见 [原始运行证据](../docs/evidence/v01-real-rugcheck-holder-2026-11-01.md)。
- **源码观察：** Blix 提供市场终端、钱包跟踪与局部交易/缺口修复，部分市场日志只保留短窗口；Pulse 有归档/采集分层，但其当前 `flush()` 在数据库确认前清空内存队列，需验证失败恢复。参见 [Blix wallet 代码](https://github.com/blixvip/blixtrade/blob/main/server/wallets.js)、[Blix journal 代码](https://github.com/blixvip/blixtrade/blob/main/server/journal.js)、[Pulse stream 代码](https://github.com/nirholas/pulse/blob/main/src/collector/solana-stream.ts)。
- **未验：** 这两个成品在**本项目**的真实隔离启动；某 Mint 的完整钱包历史/实际资金边；同签名多钱包场景无漏记/重复计数；跨 Mint 连续监控；Grok Bot 自然语言运行。
- **三条可执行路径：**
  1. **A（第一候选）**：Blix 作为终端，先做一条只读 Mint 深度调查；优点是业务 UI 多，代价是数据覆盖和账目语义需要专项验。
  2. **B（竞争候选）**：Pulse 为主体，侧重数据库/历史调查；需要先解决其队列失败后的重试和账目一致性问题。
  3. **C（兜底/基线）**：利用现有 PR #16 的公开只读 Mint 报告先验证深度调查，不依赖主体上线；不能以此替代完整终端选型。
- **当前最优动作：** 同一枚已验证 Mint，优先审查/安全运行 Blix 的只读功能并实测报告适配；Pulse 做对应覆盖对照，同时保留 PR #16 的真实供应商基线。任何一方未通过，说明失败性质并重新判断。
- **推翻条件：** Blix 无法隔离写/交易能力、依赖不合理、钱包/历史缺口导致调查无法可信地完成，或 Pulse/其他成熟成品在同一场景明显具有更低的集成与运行成本，则撤销“Blix 第一候选”。
- **不要做：** 不为实现目标变化再造一个通用 Agent 内核、固定12项目标本体、六个 Bot 或自动审批系统。

## 6. “继续”与新的简短想法怎样触发实际工作

当用户只说“继续”，AI 读取最近 **真实的**目标/产品状态/提交/运行证据，选择最能降低最终目标差距且信息价值高的可授权动作并执行。完成后再问：本轮发现是否改变了上层目标？是否有更成熟路线？是否有值得停止的旧方案？在回答结尾给出新认识、候选（必要时）、首选、反证条件和实际交接。

当用户说“我又有个想法”，AI 判断是细化、扩展、替换还是方法变化；与已知原始目标连接后提出 2–4 条真正不同且可行的路线。对一般可逆改进不用反复索要技术决策；重大方向由用户选择。

### 这份记录自己怎样被检验
不能仅通过文档存在宣称形成了“目标演化智能”。使用 [首个决策及业务验收案例](../docs/evidence/goal-evolution-first-product-pilot-2026-11-05.md)：核对 AI 是否识别目标层级、主动找到未提问题、证据支持方案推荐，以及是否在任务授权内实际完成后续动作。若没有运行/对照证据，状态保持设计和源码研究，不宣传为自治 Agent 通过验证。
