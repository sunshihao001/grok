# Solana Meme｜产品体验、UI 与信息架构 V0.1

> **状态：设计规格，不是已经开发的网页或Grok应用页面。** 当前已实测的是工程 PR #16 的只读命令和报告。此文件设计用户如何查看、追问、导航和核查信息；专业研究内容继续来自原知识体系，不拷贝也不删除。关联的机器导航入口：[knowledge-navigation.v1.json](../knowledge/system/knowledge-navigation.v1.json)。

## 1. 两种界面，不能混成一套

1. **用户界面（Presentation UI）**：用户以简单命令/自然语言进入，在 Grok 对话内先获得概要，再展开 Mint、钱包、网络、异常和证据。原有 `report.md` / `report.json` 是可直接复用的报告载体，不需要先制作新网页。
2. **AI 知识界面（Knowledge Access UI）**：AI 根据问题选择正确的研究专题、专家视角、源码/参考资产和真实运行证据，通过机器索引返回**路径与适用条件**；不会把文件标题当成知识已验证，更不会把专家登记当成真实 Bot 调用。

这两个界面的核心联系，是共享一个任务与证据语义，不是复制一套知识数据库。

## 2. 用户体验目标与路径

**一句话目标**：用户表达“看这个币有什么异常”，系统应说明能看到什么、哪个来源、何时获取、为什么值得关注、还有什么未知；不能让用户先选择RPC、Bot或D01–D12。

正常路径：

```text
用户：分析 <Mint> 或“追踪这个币的钱包”
  → 解析目标和任务（不让用户先选技术栈）
  → 查可用程序/数据、已有来源与成本限制
  → 展示“现在有的事实/来源/时点/缺失”
  → 根据问题展开钱包、资金关系、群体异动或机制研究
  → 需要解释时按需选知识与专家视角
  → 报告证据、竞争解释、失败原因、建议观察项
  → 可继续追问/复查；无数据明确说明，而非给0或伪信号
```

**入口优先级**：命令/对话 → Markdown/JSON可读报告 → 以后若需求明确，再考虑交互图/网页看板。现阶段不因为 UI 设计就新增前端框架、数据库或部署服务。

## 3. 信息架构（7类视图是同一产品的可折叠信息区，不是7个App）

| 视图 | 用户首先看到什么 | 继续展开 | 数据/研究对应 | 当前交付状态 |
|---|---|---|---|---|
| 命令中心 HOME | 输入目标、最近报告、采集状态 | 当前任务、失败/继续入口 | Grok命令及交接设计 | **仅设计；Grok未验收** |
| Mint总览 MINT | Mint、池、流动性、供应商风险/Holder候选、采集时间 | 各数据源、Creator线索和异常备注 | `mint_v01.py` / RugCheck / DEX | **真实供应商只读报告已验，非交互页面** |
| 关键钱包 WALLETS | 地址、角色候选、Token Account 与 owner区分 | 持仓、转账/Swap待确认、可见时间 | D04/D06、旧qb-矩阵、Million候选 | **供应商候选可读；真实历史链不完整** |
| 资金网络 NETWORK | 关系边、方向、金额/Token、来源、可信边界 | 公共Hub反例、时间窗、跨Mint关系 | D05/D06、RugCheck/Million候选 | **未完成真实关系验收** |
| 异动观察 ALERTS | 观察组、变化、窗口、数据覆盖/断流 | 事件明细、正常对照、重复发生 | D07、`wallet_batch_monitor.py` | **仅离线算法；非真实持续监控** |
| 专业研判 INVESTIGATIONS | 已知事实、可能机制、竞争解释、待核查项 | 阅读相关研究专题/来源/反证 | 22专家视角按需选，12域知识 | **知识存在；AI/Grok自动研判未实测** |
| 系统状态 SYSTEM | 来源新鲜度、429、权限/费用限制、程序版本 | 日志、运行/离线区分、故障恢复 | D10/D12、工程运行记录 | **目前只有部分实测记录；统一界面未实现** |

当前尽量沿 **“一份Mint报告中的多个区块”** 落地，而不是先把七个视图分别开发。

## 4. 首屏与详情的文本线框（设计示例，非真实行情）

```text
┌──────────────────────────────────────────┐
│ Solana Meme · 只读研究                    │
│ [输入 Mint / 钱包 / 自然语言问题]          │
│ 最近任务 · 来源状态 · 查看历史             │
├──────────────────────────────────────────┤
│ [Mint总览] [钱包] [资金关系] [异动]        │
│                                          │
│ 当前证据：来自哪些供应商？何时获取？      │
│ 关键观察：哪些是事实，哪些仅为候选？      │
│ 已知缺失：历史/owner/交易/覆盖范围        │
│                                          │
│ [查看原始来源] [查看解释] [深入追问]      │
└──────────────────────────────────────────┘
```

在手机/Grok对话中，默认展示 **简短摘要 → 可按需展开的证据与解释**。真实数据中必须展示完整 Mint 或可复制地址，避免只看截断地址误操作。专业术语提供短解释，不让用户读完152个知识问题才能理解结果。

## 5. 信息层次与交互契约

从数据到UI采用四层，且分清**现存字段**和**拟定展示要求**：

1. **来源层（Raw）**：来源标识、Mint/地址、原始引用或可核查JSON位置、采集时间和失败码。原始响应不得直接混入长期知识作为确定规律。
2. **观测层（Observation）**：池/Token账户/交易/转账/数值、事件时间与可得时间、缺失及覆盖程度。供应商“聪明钱”仅标签；Token Account不等于人。
3. **解释层（Interpretation）**：引用的知识/专家视角、机制与替代解释、哪些观察会推翻解释。不能自动从相关性升级为同一控制者。
4. **行动层（User Action）**：查看原始报告、继续调查、加入观察清单（未来）、比较历史；不提供默认自动交易、付费或私钥操作。

对每个结果区块推荐显示：

```text
标题 / 对象类型 / 观测摘要
证据级别：真实原始链上核验 | 供应商返回 | 离线fixture | 假说 | 不可用
来源与时间：source + retrieved_at；事件另标 event_at
覆盖：哪些字段或窗口可用？哪些UNKNOWN？
解释与反例：为什么值得注意、什么正常情形也会相同
操作：复查来源 / 追问 / 查看历史（仅功能存在时可用）
```

**错误/空状态必须设计**：HTTP429、API超时、供应商缓存、无数据、没有权限、跨链错误、Token/owner无法确认、监控断流、Bot未部署、费用超限。空数据不展示为“无异常”“没有仓位”或“安全”。

## 6. UI组件复用与边界

- 初步组件：`SourceStamp`（来源/时间）、`CoverageNote`（覆盖/缺失）、`ObservationTable`（地址/事件/金额/时间）、`RelationEdge`（资金/Token关系与未证实身份）、`Interpretation`（机制/反例）、`RunStatus`（运行失败/恢复）。**这是设计命名，不是仓库已有前端代码**。
- 图形网络是可选展示形式，**表格及明确关系边已能满足初步核查**；未有可靠资金边不生成漂亮的“庄家图”。
- 单一证据内容只维护一份源记录，UI只引用源ID/路径。不同视图互相跳转同一 Mint/钱包/事件，防止历史结论漂移。
- 权限层面默认只读；来源价格及执行成本是研究内容而非自动下单按钮。

## 7. AI 怎么从界面问题调用已有知识

机器导航 `knowledge/system/knowledge-navigation.v1.json` 中每个任务包含：
`goal/cues/domains/experts/knowledge_files/engineering_ids/reference_ids/ui_views/expected_output`。

AI可用`project_navigator.py --question`取得短名单，再以`--open-path`只读打开白名单内原有知识（带SHA256和截断标识）；并不是自动调用外部Bot或实时取数。

AI 实际使用顺序：
- 从用户目标辨识研究/产品/错误排查/解释任务，关键词只给候选，不做最终裁决。
- 先读取最相关的 1–3 个原有专业文件，遇到疑问再沿本体关系扩展；不强制载入全部专家。
- 需要程序能力时查对应**工程分支**的源码/测试/实测，不能把知识分支的原型当已经集成PR #16。
- 需要外部能力时查65项参考资产与功能级复用台账；K1来源索引与REF资产登记是不同用途，不合并数量。
- 形成回答或完成允许的执行，明确研究认识与实际运行结果；确有新知识再修订原专题。

## 8. 设计验收顺序（不强制锁定研究方向）

1. **导航验收**：随机选 Mint查询、资金群、异常、UI设计、经济机制、Grok运行等真实自然表达，能指向对应专题/专家/代码/状态；发现旧入口冲突不反复复制整库。
2. **报告信息层次验收**：复用现有真实V0.1 JSON/Markdown检查来源/时间/UNKNOWN是否能完整表达；不编造新字段。
3. **真实功能优先**：V0.2有可核查关系边再做NETWORK展示；异常连续采集通过再提供ALERTS运行视图。
4. **Grok入口验收**：经正式授权与固定SHA，只读命令能完整回传报告/状态/失败，再考虑看板；任何一步不达标都不能把设计稿标成部署完成。

**产品设计的完成判断**：用户不知道技术栈也能理解、查证和追问；AI不会拿错知识版本、把参考代码当可用功能，或把知识目录当产品界面。

## 9. 以现成同行产品实际代码重新收束UI：少页面、重闭环（2026-11-01）

这部分是对本文件前面七种**信息视图**的改进，不是增加第八种或第九种页面。已直接核对 [Million现有Web路由](https://github.com/Kelows/million/blob/c89ad07caaf70773d40b45943e136eadc4f946a5/apps/web/src/router.tsx) 与[实际产品使用手册](https://github.com/Kelows/million/blob/c89ad07caaf70773d40b45943e136eadc4f946a5/docs/GUIDE.md)、[HoldTech跨Mint对比实现](https://github.com/co-numina/holdtech/blob/a75e214bf1ee0a8803eb7d93336be98c481c2db9/app/api/holder-overlap/route.ts)：

- **入口一：研究一个Mint**。借鉴HoldTech的单地址输入与Million的Token/Discover详情，但优先展示**真实来源、时间、池/AMM排除及未知项**，而非未经校准的“安全分”或K线。已有`mint_v01.py`和`project_workspace.py`可输出本入口所需的Markdown/JSON；网页不是前置。
- **入口二：比较多个Mint/钱包**。借鉴HoldTech `holder-overlap` 和Million `funding/flows` 的跨资产调查习惯。现已有`cross_mint_holders.py`对2–5个已存Mint只读报告比较**供应商Owner候选地址重叠**；显示每Mint样本总量/排除数/时间/来源hash、每对重合地址及原路径，**不**默认展示“同一庄家”。
- **入口三：观察与复查**。借鉴Million `Live/Flows` 的使用方式，但本项目当前真实持续流缺失，所以先展示“未启用/来源不可用/历史样例”及当次任务日志；不能做一个会自动刷新但底层并无数据的看板。
- **每个入口共用“数据证明栏”**：当前是供应商缓存、RPC验证、模拟测试还是没有来源？最近采集时间？哪些字段不可信？任务从哪条代码/哪次提交产生？依据哪些原知识原文做解释？
- **Grok自然语言**只作为这些已有业务命令的友好入口；不是另外一套重复的数据研究架构。未来如要Web，可复用Million的按任务分组的路由思路，暂不引入NestJS/Next/React构建复杂后台，更不引入自动下单。

### 9.1 当前已具有实际代码的对照输出

```bash
# 前提：已经保存了两个真实或明确标成模拟的V0.1 report.json
PYTHONPATH=src python -m solana_meme_os.cross_mint_holders \
  /path/mintA/report.json /path/mintB/report.json \
  --out-json /path/compare.json --out-md /path/compare.md

# 单Mint保存的报告 + 原有研究原文（不重新请求第三方）
PYTHONPATH=src python -m solana_meme_os.project_workspace \
  --report-json /path/mintA/report.json \
  --question "这些Holder和资金关系有哪些可能的解释" \
  --intent FUNDING_ENTITY --out-md /path/context.md
```

第一条功能是本项目自主实现的**受限本地复用业务流程**，不是启动HoldTech接口；第二条是已有源码/研究桥接。两者离线测试不代表真实资金图已经存在。

### 9.2 设计验证清单（避免再做漂亮空壳）

- 每个Mint页必须能回溯它对应的 **报告SHA/原供应商哈希**，没有来源必须显示缺失。
- 每个跨Mint重叠地址必须展示**哪两份样本的哪行供应商字段发生相同地址**，不能凭计数给“资金控制”结论。
- 将Token账户、Owner、池Vault、其他公共基础设施分开；服务商来源未知时保留不确定性。
- AI总结必须能打开原领域知识的**行号/哈希**，并明确“原文候选 ≠ 已证市场解释”。
- 真实连续监控没有通过数据与断流验收前，“告警/Live”页**只能呈现状态或模拟演示**，不伪造动态更新。

这组改进改变的是**现有视图怎样组织和实际填数据**；七个旧视图仍可以作为详情/子栏目，但不需要七个独立Bot或七套后台。
