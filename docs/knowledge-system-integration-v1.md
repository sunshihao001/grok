## 1. 统一项目概念

**观察对象**：事件、交易、地址、Token Account、Mint、池子、流动性、资金与库存路径、时间窗。  
**候选解释**：多个独立机器人、公共基础设施、同一市场事件驱动、共享资金或执行者、疑似受共同控制的经济实体。  
**研究结果**：能量化的行为事实、异常相对基线的偏离、区分竞争解释的证据、随时间变化的市场影响及可证伪的预测。  
**下游行动**：忽略/观察/进一步调查/风险预警/纸面交易候选。异常并非庄家确认，庄家假设并非盈利信号。

系统主线：

```text
市场发现（新 Mint / 迁移 / 热点 / 跨币重复模式）
 → 已核实、去重、带时点的原始事件
 → 多时间尺度的钱包群体异动（数量、金额、时间）
 → 资产图 + 经济主体假设图（不合并证据层次）
 → 同阶段正常基准、竞争解释、反证与未知字段
 → 流动性 / 库存 / 价格 / 开发者 / 市场阶段联动
 → 风险与预测研究 → 纸面执行和净收益审查
 → 告警、复盘、反证回流与知识版本修正
```

该链条是系统功能关系，不要求研究者每次机械走完所有步骤。尤其不要以固定规则/现有卡片禁止提出新机制。

## 4. 新系统模块与代码事实对齐

| 模块 | 运行现状（2026-10-31 分支审查） | 下一次可验收的增量 |
|---|---|---|
| M0 市场覆盖与数据适配 | `gmgn_collect.py` 只读初始原型，外部来源可用性未认证 | 明确真实 Mint/交易集，记录覆盖与时间及响应失败 |
| M1 规范化原始事件 | `market_observatory.py` 目前**接受外部已规范化事件**，本身不解析 RPC | 确认原始签名/指令类型、Token 单位和可得时间，加入真实只读样本 |
| M2 时间窗/群体候选 | `market_observatory.py` 已实现窗口聚合、same-slot、fanout、token-consolidation、funding-to-buy 的**确定性候选** | 做覆盖率、重复事件、异常窗口边界与回放测试；不直接输出“庄家” |
| M3 资产图和主体关系 | 可从事件中产出部分候选关系，缺稳健跨 Mint/跨期图及 hub 排除 | 构建双图并以正常/公共设施做反证 |
| M4 统计异常与正常基准 | **无**可靠总体、正常基准、null 模型或校准概率 | 设计样本/分母与条件对照、识别误报 |
| M5 市场状态 | `monitor.py` 有单 Mint 流动性/Top10 快照差分；旧理论较丰富 | 链接窗口事件、流动性、holder、阶段变化和时效 |
| M6 机会/风险 Gate | `rules/monitor.v0.json` 是未验证示例参数 | 先模拟并分开异常风险与独立交易效力，保留人工审批 |
| M7 Grok 解释与追踪 | `knowledge.py`、`research.py` 是确定性来源选择；多个 Skill 文档存在 | 盲测实际 Grok 的来源选取、竞争解释、反证和监控摘要 |

**一条重要工程约束**：`market_observatory.py` 是**输入已验证/可信结构的聚合器**，并不证明任何输入为真实 Solana 链上数据，也没有真实行情/图谱流式订阅或 Jito bundle 来源。测试不等于外部效度。

## 5. Skill、文档和知识的统一入口

- **总研究入口**：`skills/solana-meme-system-intelligence/SKILL.md`；先确定实际市场问题和竞争机制。
- **高深度写作**：`skills/solana-meme-expert-writing/SKILL.md`；深读原文，围绕真实问题写可核验的机制论证。
- **现有知识检索**：`skills/solana-meme-knowledge/SKILL.md` + `knowledge/catalog.v1.json`、`source_index.v1.json`；15 张旧卡是历史知识入口，非全域认知边界。
- **监控与状态保存**：`skills/solana-meme-monitor/SKILL.md`、`monitor.py`；明确与 `market_observatory.py` 的输入口径区别。
- **总体运行角色**：`BOTS.md` 负责研发分工，一个只读 Monitor Bot 为最终运行目标。
- **外部知识**：来源矩阵记录真实文件与提交；需要时加载，不批量复制第三方文档、不导入旧 Hermes runtime。

## 6. 第一轮集成的通过标准

1. README、CONTEXT、BOTS、design、skills、docs、knowledge、rules 对项目范围无相互冲突定义。
2. 每种已有 Python 入口能说明输入、输出、输入真实性等级及未实现功能。
3. 合成数据能复现多钱包同 Slot、多账户注资、Token 归集；重复事件、未来时点、单位错和公共节点不能产生“确认操盘”结论。
4. R001–R003 的钱包仓位研究被保留并降为专项，不能被误认为全市场系统已经验证。
5. 能给出下一轮真实数据接入和正常/异常校准的具体需求。
6. GitHub 文件和测试经过检查；真实 Grok 云 Bot 未部署、未授权生产规则或下单。

**简短认知表达：** 以真实链上事件为本体，洞察钱包群体和资金循环；在正常基准与竞争解释中识别异常，再把有用的机制转换为可验证、可扩展的监控能力。
