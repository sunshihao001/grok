# Solana Meme 知识体系架构 V2.0｜全领域本体、认知层级与运行能力统一规范

> **状态**：当前草案分支的知识架构主规范；不是生产系统部署证明。  
> **研究主线**：从全市场事件重构行为关系，从资金网络发现隐藏机制，以真实数据和竞争解释不断深化专业认知，将知识转化为可验证的监控与研判能力。  
> **架构决策**：V5 定义研究思维；V4 定义运行组织；本文件定义知识与认知的组织方式。三者互补，不再互相替代。  
> **机器索引**：[architecture.v2.json](../knowledge/architecture.v2.json)；**运行边界**：[dual-loop V4](dual-loop-research-runtime-architecture-v4.md)；**研究宪章**：[economic-mechanism-discovery V5](economic-mechanism-discovery-charter-v5.md)。

## 1. 先给结论：当前系统有几种不同的“层级”，必须拆开

过去最容易发生的结构错误，是把知识领域、研究步骤、软件模块、专家角色和 Bot 运行职责混成一张层级图。它们回答不同问题，不能一一对应。

| 结构 | 解决的问题 | 当前正式定义 | 不能误读为 |
|---|---|---|---|
| **L0–L7 知识架构层** | 我们需要理解哪些事实、机制、判断和知识治理 | 本文件第 2 节 | 每个事件必须顺序跑完八关 |
| **12 个知识领域** | 研究世界由哪些专业对象组成 | 专业分区 | 12 个 Agent |
| **17 类专家能力** | 谁具备哪一种研究方法、能交付什么、能反驳什么 | expert-capability-map.v1.json | 17 个云端 Bot 或 17 票投票 |
| **S0–S7 研究阶段** | 一个具体问题的研究工作怎样推进、回溯和验收 | 专家协作规范 | 软件组件 |
| **M0–M7 产品能力** | 最终监控产品需要哪些运行能力 | 全市场监控范围文档 | 已实现的八个模块 |
| **V4 快慢双循环** | 大量事件如何用低成本监控，少量重要事件如何深研 | 运行架构 ADR | 知识领域的层级 |
| **六个研发 Bot 职责** | 开发、审计和发布工作如何分工 | BOTS.md | 17 类专家能力 |
| **最终运行入口** | 生产环境实际由什么进程/云 Bot 执行 | 目标为一个只读 Monitor + 一个按需 Research Manager | 当前已经部署 |

**必须保持：L/S/M 三套编号不同义。** L 是知识依赖层，S 是研究流程状态，M 是产品软件能力。它们可以相互映射，但不能直接替换。

## 2. 八层知识架构（L0–L7）

这些层是**知识依赖与判断边界**，不是固定串行流水线。市场事件可以从风险、开发者、LP、跨 Mint 资金等任意入口进入；缺什么证据才回到对应层。

### L0｜治理宪法与认识论边界

所有研究和程序共享的最高约束：
- 不把未知当零；不把未查询当没有；不把供应商标签当链上事实。
- 地址、Token Account Owner、程序、服务商、实际执行者、经济受益人分开。
- 观察、资产流、主体假说、统计偏离、因果机制、市场效用、净交易收益分别陈述。
- 保留 source provenance、时间可得性、单位、覆盖、版本与反例。
- 同 Slot 不等于 Jito Bundle；Token Transfer 不等于 Swap；余额减少不等于 SELL；余额增加不等于外部注资。
- 仅只读/纸面研究；不读取私钥、不签名、不广播、不自动下单。
- 错误事实可直接撤回；不允许“综合评分”覆盖源证据冲突。

**对应资产**：AGENTS.md、CONTEXT.md、claim contract、规则发布纪律。  
**性质**：横向约束，任何层都不能越过。

### L1｜市场本体与观察对象

先确定世界中有哪些对象及其关系，避免“钱包”“资金”“买卖”等词混用：
- **链与协议**：cluster、slot、block、program、program version、commitment。
- **执行对象**：transaction/signature、transaction index、outer/inner instruction、account meta、logs、compute/fee。
- **账户对象**：wallet address、Token Account、owner、authority、custody/service account、program-owned account。
- **资产对象**：SOL/lamports、WSOL、SPL/Token-2022、Mint、token amount/decimals、LP position、pool reserves。
- **市场对象**：launch/curve、migration、AMM pool、route、quote、trade、liquidity、price impact。
- **行为对象**：funding、transfer、swap、LP add/remove、fee accrual/claim、inventory consolidation、deployment、re-use。
- **分析对象**：event、time window、cohort、wallet role、campaign/motif、baseline、mechanism hypothesis、claim、risk state、paper result。

同一地址可以在不同时间承担不同角色；一个经济实体可能轮换多个地址；多个独立用户可以共享一个基础设施节点。**本体先允许关系复杂和未知，不先把地址归并成“庄家”。**

### L2｜数据、执行语义与证据来源

回答“到底观察到了什么、数据从哪里来、何时可用”：
- 原始来源和来源版本：RPC、gRPC/indexer、OKX/GMGN 等供应商数据，记录权限、查询条件、覆盖、延迟、缺失和错误。
- 交易事实：signature、slot、instruction path、program、account keys、pre/post lamports、Token balance changes、logs。
- 经济事件解码：System Transfer、Token Transfer、Swap、CloseAccount/WSOL、LP、桥/程序收款、Creator Fee 等；新 Program 可以触发 OPEN_DISCOVERY。
- 时间语义：observed_at / available_at / received_at / produced_at / decision_at 分开；晚到事件要修订窗口，但不能回填当时不可得的信息。
- 金额语义：整数 raw units、decimals、lamports、费用、rent、Token 余额；保留未解释残差。
- 证据分类：SOURCE_ASSERTION、SOURCE_DERIVED、RAW_RPC_OBSERVED、NORMALIZED_EVENT、DERIVED_METRIC；不同类别不能互相冒充。

**关键输出**：Canonical Event Ledger、source/coverage report、解码器版本、事件分类边界。  
**当前最大缺口**：真实 M1 RPC/多源采集与指令级解码尚未完成。

### L3｜行为结构、钱包角色与经济资产网络

回答“这些事件如何组织成可解释的行为过程”：
- 钱包生命周期和时变角色：funder、relay、trader、sniper、recipient、router、deployer-related、fee collector 等；每个角色都需证据与时间范围。
- 群体行为：funding fanout、co-buy/co-sell、same-slot sequence、joint signer、Token consolidation、跨 Mint 重复 motif。
- 资产图与经济主体假说分离：先记录 SOL/Token/LP/费用的真实资产边，再独立提出同控、共享服务、独立机器人、公共事件驱动等假说。
- 资本循环：外部资金、已有仓位释放、LP、WSOL/CloseAccount、Creator Fee、真实 Swap 收入、库存转移、资金回流和再部署分开。
- Token Account owner 对齐、CEX/bridge/router/public hub 排除、first-funder 历史覆盖和未知状态保留。
- 开发者/发行网络：创建签名、权限、手续费配置与领取、部署历史、跨 Mint 地址轮换。

**关键输出**：有类型的事件序列、资产事实图、钱包角色时间线、经济主体竞争假说图。  
**禁止跳跃**：资产边不等于控制边；共源不等于同控；Token 归集不等于已卖出。

### L4｜统计推断、正常基准与对抗性解释

回答“这种行为在什么条件下真的偏离正常生态”：
- 明确总体、分母、未触发样本、抽样机制和可观察覆盖；不只研究被告警选中的钱包。
- 按协议、发行阶段、流动性、热度、钱包活跃度、机器人密度、时间与采集覆盖进行条件分层。
- 以 null/permutation、匹配对照、跨 Mint holdout、时间外验证和相同告警预算比较检测方法。
- 分开计算交易数、事件数、独立 owner 数、SOL/Token 金额、集中度和极端值贡献。
- 处理多重检验、图巨型连通分量、公共 hub、同源重复特征、概念漂移和错误标签传播。
- 缺分母、历史不足或 source conflict 时输出 UNASSESSED/UNKNOWN，不能输出校准异常概率。

**关键输出**：条件偏离、误报/漏报、覆盖率、baseline version、null comparison、漂移状态。  
**当前最大缺口**：代表性全市场总体与正常机器人生态基准尚未建立。

### L5｜经济机制、市场因果与反事实

回答“为什么会出现这种结构、不同机制会留下什么不同痕迹”：
- 机制生成从事实矛盾、频率/价值反转、资金图与库存图冲突、历史覆盖缺口、价格/池储备不守恒等触发。
- 每个机制至少有 H1/H2/H3 竞争解释、独立预测、判别性签名/观察、正常对照、失败条件和适用范围。
- 将自身交易造成的价格冲击与后续独立需求分开；把 LP/WSOL/费用/桥/复合程序等资产路径放回真实执行语义。
- 生命周期、FCZ/POC/AVWAP、迁移、池深、供需与库存必须区分事前候选和事后定义。
- 专家分歧用于发现数据/本体缺口，不用多数投票生成事实。
- 机制状态可为逻辑/协议错误、样本内被反证、未测试、限定支持、样本外复现；不得用单个源表案例升级全市场结论。

**关键输出**：版本化机制假说、因果图/反事实、最小判别实验、结论撤回范围。  
**当前研究资产**：HX01–HX08 八个候选机制；它们是研究登记，不是已证实的市场规律。

### L6｜按用途分开的市场能力与行动资格

同一机制可服务不同目的，不能只以“能不能跟买”衡量知识价值：
1. **市场发现**：提高新 Mint/迁移/跨 Mint 事件的覆盖。
2. **群体监控**：识别值得调查的资金/交易/库存时序结构。
3. **开发者与资本网络监控**：追踪重复角色、费用领取和资金再部署候选。
4. **风险预警**：权限、流动性、库存、集中度和卖压风险。
5. **市场状态研判**：价格形成、池深、外部需求和生命周期。
6. **预测研究**：判断某机制对未来事件/市场状态是否有独立增量信息。
7. **纸面交易经济**：另需决策时点、真实报价、延迟、成交、费用、MEV、容量、退出和失败样本。
8. **实际交易**：不属于当前授权范围。

每一种用途必须单独设指标与验收。**统计异常有效 ≠ 因果解释正确 ≠ 风险预警有效 ≠ 预测有效 ≠ 净交易收益为正。**

### L7｜知识沉淀、QA、版本与反证回流

让系统能够纠错，而不是只增加知识文件：
- 每个重要结论有 claim_id、类型、来源、时间、生产专家、假设、竞争解释、依赖 claim、有效状态。
- 原始事件不可静默覆盖；派生结论 append-only version；新证据到达时标记受影响下游 CONTESTED/RETRACTED/SUPERSEDED 并重算。
- 研究案例与知识卡分离：案例保存完整样本和结果；卡片保存可迁移机制、证据要求、反例与下一步。
- 来源登记、许可、commit、path、版本和使用边界必须可追溯。
- QA 有独立挑战权；知识升级需要重复验证和人工审查。
- 运行规则、研究假说、知识卡、Skill 和部署状态分别版本化；一个研究报告不能自动改变生产规则。

**关键输出**：claim dependency、review record、case archive、知识卡/来源索引更新、可回滚的规则版本。

## 4. 三套流程：产品模块 M、研究阶段 S、运行双循环 V4

### 4.2 研究阶段 S0–S7（一个 Case 怎样研究）

| 阶段 | 研究动作 | 关键产物 |
|---|---|---|
| S0 | 定义问题、总体、分母、决策时点、资源预算 | study_contract |
| S1 | 来源/原始交易/指令语义与数据完整性 | typed_events、coverage |
| S2 | 行为窗口、钱包角色、资产关系 | event_motifs、资产/主体候选图 |
| S3 | 正常基准、对抗性解释与统计检验 | baseline、null、偏离/未知 |
| S4 | Token/开发者/库存/流动性/生命周期 | market state、risk facts |
| S5 | 竞争机制、因果推演、主动反证 | HX版本、判别性取证 |

研究可并行、跳转和回溯；不允许绕过 L0/L2 的证据边界。

### 4.3 V4 运行组织（如何在运行时安排资源）

- **快循环**：确定性来源接入、事件解码、去重、窗口和候选。
- **慢循环**：按事件价值生成有限 Case，路由所需专家与只读签名调查计划。
- **审计/学习回路**：独立 QA、claim 依赖回溯、知识修订和人工发布。
- 初始目标是一个只读 Monitor + 一个按需 Research Manager；专家是知识/方法能力，不要求 17 个 Agent 常驻。
- 现有 research_dispatch.py 只生成调查计划；没有实际 RPC、Bot handoff、持久任务队列或自动告警。

| 专业领域 | 主要知识层 | 典型专家能力 |

| 协调/Sybil/捆绑候选 | L3–L4 | adversarial, event, statistics |

| 微观结构/流动性 | L3、L5–L6 | liquidity, regime, execution |
| 库存/筹码/经济控制 | L3–L6 | inventory, graph, risk |

领域可横跨多层，不要求一领域只属于一层。

| 研究阶段 | **8 个 S0–S7** | 单个 Case 的开放式研究状态 |
| 专家场景路由 | **9 个** | 已编码的典型问题组合，不是穷尽市场所有机制 |
| 专家交接关系 | **40 条 L01–L40** | 类型化交接/反证契约；不代表自动执行 |
| 机制假说 | **8 个 HX01–HX08** | 可证伪研究候选，不是市场已知规律 |
| 研究单元 | **7 份**：R001、R001B、R002、R003、R005、R006、R007 | 历史案例/机制研究；仓库当前无 R004 文档，不补造编号 |
| 外部源驱动新知识 | **6 个 KX-01–KX-06** | 已转化为本轮知识卡，仍按来源边界使用 |

本轮新增的 9 张知识卡把 R005/R006/R007 的发现和 KX-01–KX-06 的跨领域方法纳入检索。它们提高的是“已有研究成果可被调用”，不是把源表派生数据升级为链上真值。

## 7. 知识成熟度：从“读过”到“能用于某个目的”

知识成熟度与 claim 证据状态必须分开。建议按**每一项具体主张/用途**而不是整个专家领域评级：

| 等级 | 定义 | 可允许的表述 |
|---|---|---|
| K0 | 主题/来源被发现 | 有待研究的方向 |
| K1 | 原始文档/源码/论文被审阅 | 已理解来源如何定义和处理数据 |
| K2 | 已转成明确变量、竞争机制、证据要求和失败条件 | 可检验研究协议/假说 |
| K3 | 用原始 RPC/独立数据对具体案例复算 | 限定样本内的事实复核 |
| K4 | 在未选择的对照总体、时间外样本和漂移条件下验证 | 可报告限定范围的统计/机制效力 |
| K5 | 对特定用途（发现、监控、风险、开发者研究）显示稳定增量价值 | 可批准该用途的只读能力 |
| K6 | 纸面执行经过决策时点、真实报价、成本、容量、退出和样本外验证 | 仅可称限定环境下的 paper edge；不自动授权实盘 |

**当前总体判断**：知识架构和研究协议较成熟（许多专题 K1–K2）；真实 RPC 独立复算、正常总体和用途效能仍是主要瓶颈。不能给整个项目一个笼统“完成百分比”。

## 10. 维护原则

- 本文是知识架构主入口；V3、V4、V5及专题报告是对应方法、运行和机制的深层文件，不互相复制为四套“总纲”。
- 数量统计以机器文件实数为准；改动卡片、来源、专家或边后，同步更新 architecture JSON 与一致性测试。
- 新研究必须说明其证据等级、分母、来源版本、适用范围、反例和下一步，不以文档篇数提升成熟度。
- 新机制不受当前 12 领域/17专家/9场景限制；确有证据缺口时新增领域或专家，不能为了架构完整而强行塞入旧节点。
- 保留历史报告，不覆盖旧结论；用 superseded / contested / retracted 明确状态和受影响范围。

**最终原则：知识架构组织认知，原始事件约束事实，竞争机制产生新问题，反证决定知识去留，运行结果决定能力是否真正成立。**
