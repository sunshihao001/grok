## 1. 目标不是一个更大的“聪明钱包列表”

用户真正需要的是多尺度行为发现：

- 在一秒、五秒、一个 Slot、几十秒、几分钟和多个发行之间，发生了什么群体事件？
- 多少笔 SOL 转账，涉及多少**不同发送者和接收者**，每次转账金额多少，总计多少 SOL？
- 几个钱包是否在获资后同时买入或卖出？其交易与创建/迁移/市场事件怎样对齐？
- 这些钱包是真正经济独立、普通 bot 集群、公共基础设施下的客户、资金调拨账户，还是重复执行网络？
- 同一群钱包是否跨多个 Token 重复出现，是否有代币归集、统一卖出和 SOL 再部署？
- 这些变化在当时究竟代表风险、市场供需变动，还是存在可检验的预测价值？
- 在什么具体的入场、退出、流动性和时间条件下，值得进入纸面交易验证，而非只描述历史？

系统不能一开始就把钱包分成“正常/庄家”两类，而应先问它的行为相对哪一个基准异常，以及它支持哪些机制。

## 4. 第一个可落地成果：批量异动观察，而不是交易预测

建议将第一条真实运行的研究链定义为 **WALLET_BURST_OBSERVATORY**（候选名称，不创建生产 Rule）：

1. 从一组真实监听的 Token、池子或发行事件中获取已经确认的交易和资金转账；
2. 按 signature + instruction_index 进行去重，并明确同一 tx 多笔转账、同 Slot 多笔 tx 的区别；
3. 以可配置时间窗聚合；计算事件数、唯一发送钱包数、唯一接收钱包数、总 SOL、典型单笔金额、共同资助者比例、首末事件时间和与创建 Slot 的差；
4. 基于同阶段、类似热度的事件生成正常基准，不能以“超过 N 个钱包”直接称庄家；
5. 对符合候选异常的窗口继续检索非公共资金路径、交易顺序、重复币种行为，并识别 CEX/交易服务商 hub；
6. 输出原始事件引用和竞争解释；未能排除的原因标 UNKNOWN；
7. 通过人为复核和历史对照后，才能评估是否应加入监控优先级或纸面交易研究。

建议首轮关注三类现象：
- **FUNDING_FANOUT**：单一或少数地址短时资助多个新钱包；
- **COORDINATED_BUY_CANDIDATE**：新钱包在资金到达之后集中买入同一 Mint；
- **TOKEN_CONSOLIDATION**：多个早期钱包向少数接收地址转移 Token。

这三种可以自然组合形成“资金注入 → 执行买入 → 库存转移”的行为路径。它们既可能是不同客户共享自动化服务，也可能是单个操作网络。需要至少一个明确的反证机制，不能预设同控。

## 5. 重要技术纠正：同 Slot 与 Jito Bundle 并非等价

[Solana getBlock/RPC JSON 结构](https://solana.com/docs/rpc/json-structures) 能给出交易位置、签名、余额/Token 变化和程序指令；这是可靠的**执行观察基础**，但不保证可以从 Slot 位置直接观察提交方式。

[Jito Bundle 官方文档](https://docs.jito.wtf/lowlatencytxnsend/) 对 Bundle 的定义是最多五笔交易、同一个 Slot 内顺序执行且具有原子性。**同 Slot 多钱包买入可能是普通独立交易、机器人一致响应、单交易多指令、特定 bundled 提交，也可能是其他调度结构。**

因此实际标签必须区分：
- `SAME_SLOT_MULTIWALLET`：源数据证实共享 Slot；
- `ADJACENT_SLOT_TX_SEQUENCE`：共享 Slot 且顺序相邻；
- `COORDINATION_HYPOTHESIS`：根据资金、时序和重复性推断的候选；
- `JITO_BUNDLE_CONFIRMED`：只有适用的独立 bundle/provenance 证据才可标记；
- `BUNDLE_UNKNOWN`：没有实际提交端证据时的状态。

不能直接把“同 Slot 四个钱包”转换为“Jito 捆绑四个钱包”。

## 6. 预警应能回答多少、什么时候、谁、为什么不同寻常

以下是**格式示意，不是真实预警**：

```text
[SYNTHETIC / RESEARCH EXAMPLE] 群体买入候选
Mint: <示例代币地址>
窗口: T-60s ~ T+30s（相对池创建时点）
观察: 14 个不同 owner，19 个资金转账，11 笔买入
资金: 资金流入合计 82 SOL；成交买入合计 70 SOL
关系: 其中 9 个地址可能同源于非公共资金节点；核验深度 1–2 跳
对照: 对照样本及条件分母尚未获得 → 不得输出显著异常
候选解释: 独立高频机器人 / 服务商批量分发 / 同一运营网络
缺口: 源节点身份、完整资金交易签名、重复样本和市场可得时点
下一动作: 追查上游注资签名，查最近相似发行的重复地址群
状态: OBSERVATION_RECORDED + COORDINATION_UNVERIFIED；无交易行动
```

实例中的金额、地址数量只说明报告如何组织，不能冒充现有监控器的实测输出。

## 7. 如何区别观察、风险与交易机会

不能从“多钱包协同买入”一步跳到“值得买”：

1. 是否为真实链上变化，是否有完整且及时的来源？
2. 是否超出同类正常市场阶段的基准？
3. 是否只是创建价格曲线、公共新闻或服务商导致的自然同步？
4. 哪些钱包持有/卖出 Token、下游库存结构怎样变化，是否存在明显退出压力？
5. 池深、流动性和交易容量是否支持预计进出场？
6. 如果信号在我们实际收到时仍有预测价值，是否通过独立时间段样本测试？
7. 扣成本后的纸面收益是否足够，失败交易和极端亏损如何记录？

当前研究状态只使用 `IGNORE / WATCH / INVESTIGATE / RISK_WARNING / PAPER_EVALUATION_CANDIDATE / PAPER_NOT_JUSTIFIED`。实际资金下单系统仍在授权范围之外。

## 8. 知识迁移和人员分工调整

- **规则/专家研究 Bot**：从跨项目知识构造问题、实证合同和竞争机制；
- **数据接入 Bot**：先明确使用 OKX、Solana RPC 或其他已有只读工具，做到事件单位、延迟、缺失和原始签名可靠；
- **钱包与图谱 Bot**：开发聚类、资金路径、同类基准、正常/异常与跨 Mint 复现；
- **市场结构 Bot**：筹码、流动性、池子/迁移/开发者与状态转移；
- **证据与机会 Bot**：先审核证据和风控，再研究纸面策略，绝不能依靠异常分数直接产生交易动作；
- **QA 与负例 Bot**：针对模拟造假、公共基础设施、共同公开触发、错时数据和同源样本泄漏主动攻击检测器；
- **最终 Grok Monitor Bot**：只消化冻结版本的监控能力及研究知识，不在生产监控时自动改写规则。

这只是现有 `BOTS.md` 六角色的**职责补充建议**，未实际增删任何 Bot。

## 9. 版本与验收

**本轮交付：** 监控定位纠正、真实 Grok 代码差距、全系统能力层级、第一条数据产品的字段与输出目标、专业写作 Skill。

**未做：** 任何真实市场全覆盖采集、实时钱包群体检测、交易条件的历史收益验证或 Grok 云端 Bot 部署。过去的 R001–R004 和离线 `position_audit.py` 保留为仓位数据审计**子课题**，不能再代表整个项目进度。

**首个运行里程碑的验收条件（待真正开发并运行）：**
- 在明确的观察集内输出完整候选事件数量和漏数/覆盖率；
- 对单事件至少能报告 `signature / slot / 时间窗 / 钱包数 / 转账数 / SOL 规模 / Mint`；
- 同笔交易或跨供应商重复事件不会重复计数；
- 资金图和角色图分离，能输出公共基础设施反例；
- 无条件改变异常结论的缺数据和延迟必须留痕；
- 事件分类和“是否值得进行纸面交易研究”属于不同判断层。

**认知引导词：** 从交易事件寻找群体行为，从跨币种资金网络揭示资本组织方式，以条件基准区分正常与异常，再检验异常能否转化为真实交易研判能力。
