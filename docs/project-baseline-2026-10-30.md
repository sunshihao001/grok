## 1. 唯一产品目标

目标不是同时训练七个“研究全才 AI”，也不是移植原 Hermes 运行时，而是：

**在 GPT 完成研发和证据审查的基础上，向 Grok 云电脑交付可固定版本、可重放、可停止、只读/纸面的 Solana Meme 专业研究和监控程序。**

未来发现正净期望的交易机会属于研究方向，不等于已经证明存在这样的策略。Phase 1 一律不下真实订单、不碰私钥、不签名、不广播，也不自动为数据支付费用。

最小优先运行形态只需要**一个 Grok 运行 Bot + 已完成的本地 Python 程序**。B01–B06 的角色设计是研究/质量制衡所用的责任边界，可以先由 GPT 在源码、任务和复核流程中实现；不要求 Grok 先建立六个研发实例或完成 C0–C4 全部课程。确有 AI 独立判断需求且能证明价值时，再增设专业 Grok Bot。B07 在完成独立发布/状态审查之前，不是正式长期监控服务。

## 5. 现有 Grok 与 Skill 的真实状态

1. 角色方面：B01–B07 已有提示与职责档案，但目前不能从仓库推断其已在 Grok 应用中创建。
2. Skill 方面：仓库当前 11 个 SKILL.md 模板目录，包含历史专业研究、知识取课、SQLite 交接和统一运行 Skill；**没有已在 Grok 私有 Skill 库中安装/启用的审计记录**。
3. 云电脑方面：官方 Grok Bot 文档描述持久云电脑 /workspace、共享 Bot 间文件/浏览器登录/命令行凭证；因此**单账户多 Bot 不提供安全隔离**。
4. 任务方面：SQLite 队列只保存/交付数据包；程序不自动呼叫 Grok 模型、不验证 CLI 使用者真实身份。
5. Routine 方面：仓库只有未启动的监控说明草稿；没有实际长时运行或成功发送监控结果的证据。
6. 研究方法方面：独立性目前是流程分工要求，不是代码隔离或已经完成的盲测。

**新的最小 Grok 部署方案**：先一个“运行 Bot”执行 GPT 已开发/固定的 CLI，返回 JSON 和错误。以后只有特定模块真的需要额外 AI 判断或独立测试时，才增设具体专业 Bot；不要以 7 个 Bot 的数量作为进度指标。

## 8. 建议的阶段规划（只有进入门槛和验收，不给虚假完成日期）

### S0｜项目认知与版本基线（当前整理）

目标：明确真正的架构、已实现能力、历史资料地位与暂缓工作。

通过条件：
- 一份当前权威索引、各体系职责不冲突；
- 将 Draft/已运行/已认证区别写明；
- 源码、知识与测试各有唯一引用位置；
- 不丢历史内容，不把旧待办当现行承诺。

**本文件建立的是 S0 审计基线，不等于所有历史矛盾都已在程序代码中消除。**

### S1｜GPT 完整交付与云电脑一次性部署验收

GPT 端：稳定统一入口、固定提交、运行环境清单、测试与错误代码、配置/回滚文档。

Grok 端：在获授权的云电脑检出确定 SHA，**只执行一个既有命令**并回报 JSON；不改写 Python。

验收：实际云电脑能完成 P0 的知识审计、SQLite 合成交接、离线 OKX 解析、monitor fixture；出现依赖/状态错误时清晰退出。通过后才能把流程保存为真实 Grok Skill。

### S2｜只读数据输入产品化

先比较 Solana 原始 RPC 与 OKX read-only DEX 的可用性、计费、副作用、覆盖和时效；不要把 GMGN 付费作为必需条件。

GPT 端：一个经过审查的只读 adapter，限定具体方法与返回大小，记录原始哈希、接收时间、Slot、数据单位、缺失和错误；配合回放及拒绝测试。

Grok 端：在用户明确授权接入后，仅负责运行及返回真实的非秘密结果。

验收：一项真实市场观测能够重放并区分“不存在 / 不可获得 / 发生错误”；没有未经审批的支付或交易副作用。

### S3｜K2 数据与专业程序

在 S2 原始来源成立后，逐批实现：钱包资金图、市场状态、真实负例、F4 预测增量、F5 净经济学、B05/B06 独立回放。

GPT 完成所有核心程序与测试，Grok 按需运行成品。每一模块都有输入、输出、失败状态和可复算验收；不能靠“AI 已理解”判断完成。

### S4｜B07 稳定只读监控

GPT 完成单写入者状态、原始来源可靠性、告警幂等、故障恢复、冻结规则加载、漂移/回滚和版本签核。

**硬门槛**：没有实测数据、冻结规则、人工审批和单写入者能力，就不启用定时 Routine；Phase 1 仍然禁止任何实盘订单。

### S5｜可选专业 Grok 多 Bot 扩展

只有已经发现**单一运行 Bot + Python 无法满足**的真实任务时，才按 B01–B06 的职责逐一增加 AI Bot 实例；以审计质量、研究产出和资源消耗衡量价值，而不是追求实例数量。

## 9. 未来每次 GPT 开发的标准交付件

以后开发前先写清“**为什么需要该模块**”。交付至少包括：

- 唯一版本：固定 Git SHA、模块/依赖来源版本、变更说明；
- 完整程序：稳定的 CLI 或 API 契约、参数、超时、退出码和 JSON 错误；
- 验收材料：真实或合成标注清楚的输入、通过/失败/缺数据/超时的测试；
- 知识与来源：按 K0/K1/K2 放在正确层，不在每个 Bot 复制全文；
- 运行边界：运行时不需要 AI 再发明代码；权限、收费、不可执行动作明确；
- 发布/恢复：运行报告、状态保存、停止条件、回滚到哪个版本；
- 审阅状态：CI 通过、独立审阅、Grok 实际验收、规则批准是**不同记录**。

完成一个模块，才决定下一模块。仓库文档不是功能；测试绿灯不是市场优势；Grok 能启动也不是长期稳定运行。

## 10. 下一步讨论前必须回答的问题

下一阶段只需要确认以下**技术事实**，不是立即铺开所有方向：

1. 真正的 Grok 云电脑能否在干净检出上运行 GPT 提供的一个命令，输出匹配固定 Git SHA 的报告？目前仍未知。
2. 对当前项目所需的 Solana Meme 实时数据，未经支付的独立 RPC 能提供哪些原始字段？OKX 需要什么授权/支付保护？目前尚无一次真实、可审计的供应商返回。
3. 哪些功能必须在 Grok 云端长期运行，哪些只要 GPT/CI 按需离线研发、Grok 临时运行即可？不要在未决定监控粒度和成本前启用 Routine。
4. 现有合成 monitor.v0 规则哪些应只作为工程测试保留？应由真实 K2、独立审查和人工审批后重新确定正式规则。
5. 实际云端任务量是否真的需要多个 Bot 或更重的调度框架？目前单运行 Bot + Python/SQLite 是优先默认。

**最接近的下一项决策：先验证 S1 云电脑单命令交付是否成立，再选择 S2 的首个真实只读来源；S3/S4 暂不提前投入全面建设。**

## 11. 权威关系、边界与维护规则

- 本文：项目**当前状态、目标、交付路径和工程优先级**索引。
- AGENTS.md：全局安全与执行约束；BOTS.md 和 design/bot-roster.v1.json：角色分工约束。
- knowledge/system/ontology.v1.json 与 filter-policy.v1.json：领域与证据结构权威，不被本文替代。
- knowledge/catalog.v1.json 与 source_index.v1.json：卡片和 K1 来源的实际数量/状态权威。
- knowledge/transfer/curriculum.v1.json：课程等级、依赖和审批状态权威。
- design/local-provider-capabilities.v1.json：数据源适配器**声明状态**；它不是网络权限隔离或已连接证明。
- 代码、测试、CI 与实际 Grok 云电脑输出：程序是否可运行的证据。
- 原始链上观察与独立复算：有关市场结论的证据；任何文档性表述都不能覆盖。

当结构或职责发生变更，先修改各自权威文件并验证，再更新本文摘要和相关索引。旧文档保留为历史，不直接删去用户的知识资产。将来新 PR、CI 或云端真实验证推进了状态，更新本文的具体审核 SHA 与实际验证记录；不能凭口头约定自行将 Draft 标为已发布。

**基线结论**：路线已经明确，且离线代码积累充分；当前最大的风险是概念层太多、文档演变产生执行路径歧义，以及没有真实数据和云电脑部署证据。接下来以“GPT 建成并测试一份成品 → GitHub 固定发布 → Grok 一条命令实际执行 → 原样反馈”为唯一主循环，按需引入 K2、专业 Skill、额外 Bot 和最终只读 Routine。


## 12. 本轮正式整理后的“唯一近期任务卡”

**目的**：这一段不是新增功能需求，也不是再给 Grok 一套课程；它把 S0 的决策收敛为一个可以在下一轮独立验收的 S1 任务，防止未来讨论重新发散。

### 已经确定、不再重复争论的架构决策

| 决策 | 当前结论 | 若要推翻需要什么证据 |
|---|---|---|
| GPT 与 Grok 分工 | GPT 完成主要研究/编程/测试；Grok 使用固定成品 | 实际任务证明某类 Grok 自主研发比 GPT/GitHub 更可靠，且有独立 QA |
| 程序技术基线 | Python 标准库 + SQLite + JSON 契约 + 固定 Git SHA | 明确的吞吐、隔离或故障恢复需求，且简单方案实测无法满足 |
| Grok 实例数量 | 先一个运行 Bot，B01–B07 为职责设计 | 必须是一个独立非确定性任务，并能通过盲测/可审计交接增加价值 |
| 数据供应商 | GMGN 非必需；OKX 只读候选、RPC 原始事实候选 | 明确的来源、费用、权限、实际字段/时效对比后再改变 |
| 知识扩展 | 旧知识保留，按需索引到程序，不让 Grok 强制学完 C0–C4 | 新真实案例证明某个知识缺口阻碍具体程序的判断 |
| 发布状态 | 开发 PR / 纸面模拟，不开启真实交易 | 必须另起权限与安全审查，不因模型自信或 CI 通过自动变更 |

### S1 交付卡（尚未在真实 Grok 云电脑验证）

- **GPT 交付内容**：一个带 40 位 SHA 的经审阅代码版本、一个固定 CLI、通过 CI 的测试和明确错误语义。
- **用户参与**：只需要授权 Grok 使用它自己的云电脑与 GitHub 访问；第三方安装、付费、钱包权限仍需单独审批。
- **Grok 执行内容**：在已知干净的固定 Git checkout 中运行以下单一命令（SHA 由 GPT 在具体交付时给出，不使用移动分支名代替）：

        python3 scripts/grok_operator.py --expected-sha FULL_REVIEWED_SHA demo

- **Grok 交回内容**：Git SHA、命令退出码、JSON 报告、测试摘要、失败错误码；不要改源码，不自动安装依赖，不启用 Routine。
- **通过判定**：实际云电脑报告 OFFLINE_DEMO_PASSED，知识审计/SQLite 合成交接/OKX 保存 JSON 解析/Monitor fixture 回放结果一致；且明确均为 synthetic/offline。
- **失败判定**：版本不符、工作树被修改、环境缺失、测试失败、状态异常或权限不足即停止。由 GPT 根据报告修复并发布新版本，不能由 Grok 临场替换工具或代码。
- **明确未通过的门槛**：真实 RPC/OKX 数据、K2 来源认证、B07 定时监控和任何盈利策略研究均不因 S1 通过而自动升级。

### 下一步研发生效条件

S1 完成后，优先由 GPT 开发**一个真实只读 provider adapter 的最小垂直链路**，而不是同时开发全部数据源、全部钱包图/Alpha 模型或创建七个 Grok App Bot。真实收费/API 行为没有经用户单独批准之前，可在 GPT/GitHub 完成模拟契约与错误测试，但不能让 Grok 擅自安装或调用可能产生付款的 CLI。

**S0 至此收口：先澄清和审核；实际 S1 部署请作为下一项单独任务执行。**
